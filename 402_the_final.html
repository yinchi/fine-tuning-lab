You will learn:

  • what was fixed before the development split was touched, and why it matters that nothing was changed afterwards;
  • how the fine-tuned model compares with the untuned one on conversations that no choice of the book was made on;
  • how much of the difference a good prompt makes up, and how much is left for fine-tuning;
  • whether the validation numbers of the earlier chapters were optimistic;
  • where the result sits among published numbers, and why that comparison is loose;
  • which comparisons of the book are validation results only.

Every chapter so far reported the validation split, the one the book’s choices were made on. This chapter is the only one that uses the development split. Its conversations were set aside at the start (Chapter 2), and its gold programs were used only to test code that has no model in it. A model’s outputs on them were not scored, and not read, until the decisions below were written down.

16.1 What was fixed first

Before any output was scored on the development split, the decisions of the book were written into the project’s plan (PLAN.md), with the commit they were made at, and a file was created whose existence is what lets the development evaluations run (the builders refuse the split until it exists, and a test fails if any chapter before this one asks for it). From then on the rule was that nothing changes because of a development number, except a bug, and a disappointing result is reported and not fixed. The decisions were:

  • The model and its training. The adapter of Chapter 12: rank 16, trained for two epochs on the train-fit conversations, with the checkpoint of the lowest validation loss, and seed 0. The rank sweep of Chapter 17 is a validation experiment and chose nothing.
  • The untuned model’s prompt. The variant that the rule of Section 11.4.2 chose on validation, e3p (a plain system message and three examples, example set 0), and e0p, the prompt the fine-tuned model is trained with.
  • The output format. The DSL of Chapter 3, with greedy decoding, no grammar, and one attempt per turn; an invalid output counts as wrong (Chapter 13).
  • The measures. Execution accuracy in both histories, with the predicted history as the headline; program accuracy next to it; a paired bootstrap that resamples whole report pages.

Six generation runs were then made, each once: the fine-tuned model, the untuned model with e3p and the untuned model with e0p, each with the predicted history and with the gold history. The scores below are computed from them.

16.2 The rule for more seeds

The fine-tuned model was trained once. Greedy decoding is deterministic, so the only noise that a second run would add is the training’s: the initialisation, the order of the data, the dropout. The book fixed in advance when that noise would be measured: if the paired interval of the fine-tuned model against either untuned system includes zero, in either history, two more training seeds are trained and scored on the same split, and the results are reported as a mean and a spread. The rule is checked below, after the table.

16.4 How much of the gap does a prompt close?

The untuned model with e0p and the fine-tuned model see the same input, so the distance between them is what fine-tuning adds. The untuned model with e3p has the best prompt that validation found. How much of that distance has the prompt already covered?

Code 
#HEAVY
from convfinqa.final_results import share_of_gap_closed

closed = {
    h: share_of_gap_closed(
        dev[("untuned, e0p", h)], dev[("untuned, e3p", h)], dev[("fine-tuned", h)]
    )
    for h in ("predicted", "gold")
}
# the prompt closes a large part of the distance, but not all of it:
# the interval stays between 1/2 and 1 in both histories
assert all(0.5 < c["low"] and c["high"] < 1 for c in closed.values())

pd.DataFrame(
    {
        "gap, fine-tuned minus e0p": [
            f"{100 * c['gap']:.1f} points" for c in closed.values()
        ],
        "covered by the e3p prompt": [
            f"{c['share']:.0%}" for c in closed.values()
        ],
        "95% interval": [
            f"[{c['low']:.0%}, {c['high']:.0%}]" for c in closed.values()
        ],

history
predicted 80.2 points 69% [66%, 73%]

With the predicted history the prompt covers 69% of the distance, and with the gold history 59%. Most of what fine-tuning adds can be had from a good prompt with three examples, and the rest, the part that the prompt cannot reach, is 24.5 points with the predicted history. Two things limit how far to read this. The prompt was developed on validation over several variants, while the fine-tuning configuration was fixed in advance, which favours the prompt. And the prompt is limited to describing the language: it does not teach the annotation conventions that the fine-tuning data show (Chapter 11), which a longer prompt could. The two routes also cost different amounts at inference: the examples make the prompt longer than the fine-tuned model’s (Chapter 13 measures it on validation).

16.5 Next to published results

The published numbers come from different set-ups, so this is a loose comparison. FinQANet (Chen et al. 2022) is given facts retrieved from the page, and its gold-facts variant and the few-shot GPT-3 of the same paper are given the facts that the annotators marked; ours reads the whole page. Our predicted history is the closest to how a published system would be used, and the gold history is an upper bound. Fin-R1 uses its own protocol (below). Nothing here is a leaderboard.

16.6 Were the validation numbers optimistic?

The choices of the book were made on validation: the prompt, the checkpoint, the grammar, the format. If a choice had fitted the validation conversations in a way that does not carry over, the development numbers would be lower. The check is the same three systems, both histories, on the two splits. The splits hold different pages, so each accuracy is resampled on its own, and the interval is for the difference of the two.

Code 
#HEAVY
from convfinqa.final_results import split_difference

VAL_SCORES = {
    ("untuned, e0p", "predicted"): get("scores_untuned_val_e0p_0_pred"),
    ("untuned, e0p", "gold"): get("scores_untuned_val_e0p_0_gold"),
    ("untuned, e3p", "predicted"): get("scores_untuned_val_e3p_0_pred"),
    ("untuned, e3p", "gold"): get("scores_untuned_val_e3p_0_gold"),
    ("fine-tuned", "predicted"): get("scores_tuned_val_main_0_pred"),
    ("fine-tuned", "gold"): get("scores_tuned_val_main_0_gold"),
}
val = {k: list(h.jsonl("scores.jsonl")) for k, h in VAL_SCORES.items()}
ci_val = {k: bootstrap_accuracy(v) for k, v in val.items()}
moved = {k: split_difference(dev[k], val[k]) for k in dev}
significant = [k for k, m in moved.items() if m["excludes_zero"]]
# the sentence below names the exception: the untuned model with the training prompt, which does not move with the training
assert significant

# nothing that validation chose is significantly worse on dev: the two
# systems that went through the book's choices (the fine-tuned model and the
# prompt picked on validation) stay within the noise
assert not any(s in ("fine-tuned", "untuned, e3p") for s, _ in significant)
# and the fine-tuned model scores lower on dev than on val in both histories,
# as selection on val would make it, though not by more than the noise
assert all(
    moved[("fine-tuned", h)]["difference"] < 0 for h in ("predicted", "gold")
)

16.7 What this chapter does not report

Only the comparison above is run on the development split. The other comparisons of the book are results on validation, reported where they are made, and the book does not claim them for the development split: the untuned prompt variants, the e3p prompt on the fine-tuned model and the extra-compute rows (Chapter 13); the DSL against Python, untuned and fine-tuned (Chapter 14); the grammar rows (Chapter 15); the merged adapter; and the rank sweep (Chapter 17). The reason is the same for all: a result on the development split is a result that is reported, once, and the more comparisons are run on it, the more of its value as a check is spent.

The result is also limited in three ways. It is one training seed, so the interval of a number is for the choice of pages and does not include the noise of training; the rule for more seeds did not call for them, but a second seed is what would measure it. The prompt of the untuned model had one example set. And the numbers are on one benchmark, with one model, so the contrast with published work is of a set-up and not of a method.

Program accuracy is lower than execution accuracy for every system, since it asks for the gold program and not only for

With the prompt it is trained on, the untuned model writes a program that runs in
`{python} sum(outcomes_pred["untuned, e0p"][k] for k in ("correct", "wrong operations", "wrong numbers", "wrong answer, right shape"))`
of its `{python} sum(outcomes_pred["untuned, e0p"].values())` turns, so most of its mistakes are the format of the

program, and the largest group is valid programs with other numbers (`{python} tuned["wrong numbers"]`). As on

label these dev errors one by one: the error analysis of @sec-evaluating-errors was done on validation, so that no
development failure was read before the freeze.

## How much of the gap does a prompt close?

The untuned model with `e0p` and the fine-tuned model see the same input, so the distance between them is what
fine-tuning adds. The untuned model with `e3p` has the best prompt that validation found. How much of that distance has
the prompt already covered?

```{python}
#HEAVY

closed = {
    h: share_of_gap_closed(
        dev[("untuned, e0p", h)], dev[("untuned, e3p", h)], dev[("fine-tuned", h)]
    )
    for h in ("predicted", "gold")
}
# the prompt closes a large part of the distance, but not all of it:
# the interval stays between 1/2 and 1 in both histories
assert all(0.5 < c["low"] and c["high"] < 1 for c in closed.values())

pd.DataFrame(
    {
        "gap, fine-tuned minus e0p": [
            f"{100 * c['gap']:.1f} points" for c in closed.values()
        ],
        "covered by the e3p prompt": [
            f"{c['share']:.0%}" for c in closed.values()
        ],
        "95% interval": [
            f"[{c['low']:.0%}, {c['high']:.0%}]" for c in closed.values()
        ],
    },
    index=pd.Index(list(closed), name="history"),
)
```

With the predicted history the prompt covers `{python} f"{closed['predicted']['share']:.0%}"` of the distance, and with
the gold history `{python} f"{closed['gold']['share']:.0%}"`. Most of what fine-tuning adds can be had from a good prompt
with three examples, and the rest, the part that the prompt cannot reach, is
`{python} f"{100 * (contrasts[('untuned, e3p', 'predicted')]['difference']):.1f}"` points with the predicted history. Two
things limit how far to read this. The prompt was developed on validation over several variants, while the
fine-tuning configuration was fixed in advance, which favours the prompt. And the prompt is limited to describing the
language: it does not teach the annotation conventions that the fine-tuning data show (@sec-baseline), which a longer prompt
could. The two routes also cost different amounts at inference: the examples make the prompt longer than the fine-tuned
model's (@sec-evaluating measures it on validation).

## Next to published results

The published numbers come from different set-ups, so this is a loose comparison. FinQANet [@chen2022convfinqa] is
given facts retrieved from the page, and its gold-facts variant and the few-shot GPT-3 of the same paper are given the
facts that the annotators marked; ours reads the whole page. Our predicted history is the closest to how a
published system would be used, and the gold history is an upper bound. Fin-R1 uses its own protocol (below). Nothing here is a leaderboard.

## Were the validation numbers optimistic?

The choices of the book were made on validation: the prompt, the checkpoint, the grammar, the format. If a choice had
fitted the validation conversations in a way that does not carry over, the development numbers would be lower. The
check is the same three systems, both histories, on the two splits. The splits hold different pages, so each
accuracy is resampled on its own, and the interval is for the difference of the two.

```{python}
#HEAVY
from convfinqa.final_results import split_difference

    ("untuned, e0p", "predicted"): get("scores_untuned_val_e0p_0_pred"),

    ("untuned, e3p", "predicted"): get("scores_untuned_val_e3p_0_pred"),
    ("untuned, e3p", "gold"): get("scores_untuned_val_e3p_0_gold"),
    ("fine-tuned", "predicted"): get("scores_tuned_val_main_0_pred"),
    ("fine-tuned", "gold"): get("scores_tuned_val_main_0_gold"),
}
val = {k: list(h.jsonl("scores.jsonl")) for k, h in VAL_SCORES.items()}
ci_val = {k: bootstrap_accuracy(v) for k, v in val.items()}
moved = {k: split_difference(dev[k], val[k]) for k in dev}
significant = [k for k, m in moved.items() if m["excludes_zero"]]
# the sentence below names the exception: the untuned model with the training prompt, which does not move with the training
assert significant

# systems that went through the book's choices (the fine-tuned model and the
# prompt picked on validation) stay within the noise
assert not any(s in ("fine-tuned", "untuned, e3p") for s, _ in significant)
# and the fine-tuned model scores lower on dev than on val in both histories,

    moved[("fine-tuned", h)]["difference"] < 0 for h in ("predicted", "gold")

pd.DataFrame(
```

The fine-tuned model is `{python} f"{-100 * moved[('fine-tuned', 'predicted')]['difference']:.1f}"` points lower on
development than on validation with the predicted history and
`{python} f"{-100 * moved[('fine-tuned', 'gold')]['difference']:.1f}"` with the gold history, and the untuned model with

data cannot tell a small optimism of selection from the difference between two samples of pages; they show that
the validation numbers were not far off. `{python} len(significant)` of the six differences has an interval that does
exclude zero: `{python} ", ".join(f"{s} with the {h} history" for s, h in significant) or "none"`. That is the
untuned model with the prompt of the fine-tuned model, which no choice of the book depended on, and it is the floor of
the comparison, so a few points of difference does not change what the chapter concludes.

## What this chapter does not report

Only the comparison above is run on the development split. The other comparisons of the book are results on validation,
reported where they are made, and the book does not claim them for the development split: the untuned prompt
variants, the `e3p` prompt on the fine-tuned model and the extra-compute rows (@sec-evaluating); the DSL against Python,
untuned and fine-tuned (@sec-python-format); the grammar rows (@sec-constrained-decoding); the merged adapter; and the
rank sweep (@sec-rank-sweep). The reason is the same for all: a result on the development split is a result that is
reported, once, and the more comparisons are run on it, the more of its value as a check is spent.

The result is also limited in three ways. It is one training seed, so the interval of a number is for the choice of
pages and does not include the noise of training; the rule for more seeds did not call for them, but a
second seed is what would measure it. The prompt of the untuned model
had one example set. And the numbers are on one benchmark, with one model, so the contrast with published work
is of a set-up and not of a method.
