15  Constrained decoding

You will learn:

  • what a grammar does to the model’s next-token probabilities, and why it can only repair syntax;
  • how a grammar for the DSL and one for Python are written and checked against every gold program;
  • how much of the gap between the untuned and the fine-tuned model a grammar can close.

A model that writes a program can write one that does not run: a stray word, a missing parenthesis, a code fence. Chapters Chapter 3 and Chapter 4 stopped short of fixing this. A grammar does: at every step, it lists the tokens that can continue a valid program, and the decoder gives every other token probability zero. The model still chooses, among the tokens that are allowed. This chapter runs the grammar on the untuned and the fine-tuned model, with the DSL and with Python.

15.1 The grammars

The DSL grammar is that of Chapter 3 in the EBNF of the xgrammar library. The Python grammar describes the forms that to_python writes (Chapter 14): assignments to v<k>, then ans = …, with numbers, names, the operators + - * / ** > and parentheses. It is narrower than the safe evaluator, so a model that follows it cannot leave the evaluator’s subset. Each has a bounded variant that limits a number to the digits the gold programs use: a grammar guarantees syntax and not termination, and with an unbounded number rule a model can keep writing digits up to the generation limit.

15.2 One decoding step

The mask is a list of the tokens that may come next. To see it, we feed a prefix to the grammar and ask which of the model’s 151,936 output tokens remain possible.

Code 
import torch
import xgrammar as xgr

VOCAB = 151936


def allowed_tokens(compiled, prefix: str) -> list[int]:
    """The ids of the tokens that may follow `prefix` under the grammar."""
    matcher = xgr.GrammarMatcher(compiled, terminate_without_stop_token=True)
    assert prefix == "" or matcher.accept_string(prefix)
    mask = xgr.allocate_token_bitmask(1, VOCAB)
    matcher.fill_next_token_bitmask(mask)
    logits = torch.zeros(1, VOCAB)
    xgr.apply_token_bitmask_inplace(logits, mask)
    return torch.nonzero(torch.isfinite(logits[0])).flatten().tolist()

At the start of an answer, 39 tokens are allowed: digits, a minus sign, a point, and the first letters of the operators and of const_. The untuned model’s own first token for the first turn, without examples, is ‘```’, the start of a code fence. It is not among them.

NoteUnder the hood: what the processor does to the logits

The model produces one score (logit) per token. Before the next token is chosen, the processor sets the score of every token that the grammar does not allow to minus infinity. After the softmax those tokens have probability zero and the others share the whole probability between them, in the proportions the model gave them. Greedy decoding then picks the allowed token with the highest score. The model’s preferences among valid continuations are untouched, and this is why a grammar can only repair syntax: it never makes the model prefer the correct operation.

The matcher keeps the parse state, so the mask is recomputed after every token. xgrammar prechecks the tokens whose validity does not depend on the parse stack and checks only the others at run time (Dong et al. 2024).

15.3 The code

A run with a grammar is the run without one, with the logits processor added: the same prompts, the same greedy decoding, one prompt at a time. convfinqa.constrained_eval holds the generator. The name of a run says which bound the number rule has (free or bounded). The runs without a grammar are the ones of Chapter 11, Chapter 14 and Chapter 12, and are not repeated.

@artifact(
    "constrained_untuned_{split}_{variant}_{seed}_{mode}_{bounds}",
    deps=["train_val_split", "eval_turns", "example_sets"],
    files=["configs/baseline.json"],
    heavy=True,
)
def build_constrained_untuned(
    out, deps, files, *, split: str, variant: str, seed: int, mode: str,
    bounds: str
):
    """Generate the untuned model's DSL answer for every turn, under the DSL
    grammar.

    Args:
        out: Output directory; `predictions.jsonl` is written to it.
        deps: The conversations and the example sets.
        files: `configs/baseline.json` (the model, the system messages).
        split: `val`, or `dev` once `configs/FROZEN` exists.
        variant: A prompt variant of `convfinqa.prompts.VARIANTS`.
        seed: The example set; 0 for a variant with no examples.
        mode: `gold` or `pred`, the history of the earlier turns.
        bounds: `free` or `bounded`, the number rule of the grammar.
    """
    import json
    import time

    from convfinqa.constrained_eval import generate_with_grammar
    from convfinqa.grammars import dsl_grammar
    from convfinqa.prompts import parse_variant
    from convfinqa.tuned_eval import split_conversations

    cfg = files["configs/baseline.json"].json()
    n_examples, kind = parse_variant(variant)
    if n_examples == 0 and seed != 0:
        raise ValueError(
            "a variant with no examples has no example set: use seed 0"
        )
    if bounds not in ("free", "bounded"):
        raise ValueError(f"bounds must be 'free' or 'bounded', not {bounds!r}")
    convs = split_conversations(
        split,
        list(deps["train_val_split"].jsonl("val.jsonl")),
        list(deps["eval_turns"].jsonl("dev.jsonl")),
    )
    examples = []
    if n_examples:
        wanted = deps["example_sets"].json(
            "sets.json"
        )["sets"][str(seed)][:n_examples]
        pool = {
            c["id"]: c
            for c in deps["train_val_split"].jsonl("train_fit.jsonl")
        }
        examples = [pool[i] for i in wanted]
    start, done = time.perf_counter(), 0
    with open(out / "predictions.jsonl", "w") as f:
        def sink(row):
            nonlocal done
            f.write(json.dumps({
                k: v for k, v in row.items() if k != "seconds"
            }) + "\n")
            f.flush()
            done += 1
            if done % 50 == 0:
                print(
                    f"{done} turns, {time.perf_counter() - start:.0f} s",
                    flush=True
                )

        generate_with_grammar(
            cfg, convs, examples, system=cfg["system"][kind],
            grammar=dsl_grammar(bounds == "bounded"),
            max_new_tokens=cfg["max_new_tokens"], mode=mode, sink=sink,
        )
    print(f"done: {done} turns in {time.perf_counter() - start:.0f} s")

15.10 Discussion

A grammar fixes the form and leaves the content, and the results above are what that looks like. Two pieces of related work are worth comparing.

  • Format restrictions can hurt reasoning. Tam et al. (2024) compare language models restricted to structured output formats such as JSON or XML with free-form answers. They report a drop in reasoning ability under the restriction, larger for stricter formats. That concerns a model that reasons in the text it writes and is then made to write it in a format. Here the output is the program: there is no free text for the grammar to cut short, and the fine-tuned model does not change under the grammar. This chapter’s runs do not test their claim.
  • FinQA’s decoder was restricted too. The program generator of the original FinQA model takes its output tokens from three sources: the tokens of the question and the retrieved facts (the numbers), the special tokens of the DSL, and tokens for the results of earlier steps. At inference time it also applies masks from the grammar of the DSL at every decoding step, to keep the program well formed (Chen et al. 2021). Its output space is narrower than that of the syntax grammar of this chapter, which lets any number be written. A grammar that restricts the numbers to those of the page in the same way is not run in this book (Section 17.7).

# Constrained decoding {#sec-constrained-decoding}

**You will learn:**

- what a grammar does to the model's next-token probabilities, and why it can only repair syntax;
- how a grammar for the DSL and one for Python are written and checked against every gold program;
- how much of the gap between the untuned and the fine-tuned model a grammar can close.

A model that writes a program can write one that does not run: a stray word, a missing parenthesis, a code fence.
Chapters @sec-dsl and @sec-tokens stopped short of fixing this. A **grammar** does: at every step, it lists the tokens
that can continue a valid program, and the decoder gives every other token probability zero. The model still chooses,
among the tokens that are allowed. This chapter runs the grammar on the untuned and the fine-tuned model, with the DSL
and with Python.

## The grammars

The DSL grammar is that of @sec-dsl in the EBNF of the `xgrammar` library. The Python grammar describes the forms that
`to_python` writes (@sec-python-format): assignments to `v<k>`, then `ans = …`, with numbers, names, the operators
`+ - * / ** >` and parentheses. It is narrower than the safe evaluator, so a model that follows it cannot leave the
evaluator's subset. Each has a **[bounded](901_glossary.qmd#gloss-bounded-grammar)** variant that limits a number to the digits the gold programs use: a grammar
guarantees syntax and not termination, and with an unbounded number rule a model can keep writing digits up to the
generation limit.

## One decoding step

The mask is a list of the tokens that may come next. To see it, we feed a prefix to the grammar and ask which of the
model's `{python} f"{151936:,}"` output tokens remain possible.

```{python}
import torch
import xgrammar as xgr

VOCAB = 151936


def allowed_tokens(compiled, prefix: str) -> list[int]:
    """The ids of the tokens that may follow `prefix` under the grammar."""
    matcher = xgr.GrammarMatcher(compiled, terminate_without_stop_token=True)
    assert prefix == "" or matcher.accept_string(prefix)
    mask = xgr.allocate_token_bitmask(1, VOCAB)
    matcher.fill_next_token_bitmask(mask)
    logits = torch.zeros(1, VOCAB)
    xgr.apply_token_bitmask_inplace(logits, mask)
    return torch.nonzero(torch.isfinite(logits[0])).flatten().tolist()


STEPS = {
    "start of the answer": "",
    "after `subtract(`": "subtract(",
    "after `subtract(5, 3), `": "subtract(5, 3), ",
}
step_ids = {name: allowed_tokens(dsl, prefix) for name, prefix in STEPS.items()}
pd.DataFrame([
    {
        "position": name,
        "tokens allowed": len(ids),
        "a few of them": " ".join(repr(tok.decode([i])) for i in ids[:12]),
    }
    for name, ids in step_ids.items()
]).set_index("position")
```

At the start of an answer, `{python} len(step_ids["start of the answer"])` tokens are allowed: digits, a minus sign,
a point, and the first letters of the operators and of `const_`. The untuned model's own first token for the first
turn, without examples, is `{python} repr(tok.decode([first_token]))`, the start of a code fence. It is not among them.

::: {.callout-note title="Under the hood: what the processor does to the logits"}
The model produces one score (logit) per token. Before the next token is chosen, the processor sets the score of every
token that the grammar does not allow to minus infinity. After the softmax those tokens have probability zero and the
others share the whole probability between them, in the proportions the model gave them. Greedy decoding then picks
the allowed token with the highest score. The model's preferences among valid continuations are untouched, and this
is why a grammar can only repair syntax: it never makes the model prefer the correct operation.

The matcher keeps the parse state, so the mask is recomputed after every token. `xgrammar` prechecks the tokens whose
validity does not depend on the parse stack and checks only the others at run time [@dong2024xgrammar].
:::

## The code

A run with a grammar is the run without one, with the logits processor added: the same prompts, the same greedy
decoding, one prompt at a time. `convfinqa.constrained_eval` holds the generator. The name of a run says which bound
the number rule has (`free` or `bounded`). The runs without a grammar are the ones of @sec-baseline,
@sec-python-format and @sec-training, and are not repeated.

```{python}
        out: Output directory; `predictions.jsonl` is written to it.
        deps: The conversations and the example sets.
        files: `configs/baseline.json` (the model).
        split: `val`, or `dev` once `configs/FROZEN` exists.
        variant: `e0` (no examples) or `e3` (three examples).
        seed: The example set; 0 for `e0`.
        mode: `gold` or `pred`, the history of the earlier turns.
        bounds: `free` or `bounded`, the number rule of the grammar.
    """
    import json
    import time

    from convfinqa.constrained_eval import generate_with_grammar
    from convfinqa.grammars import python_grammar
    from convfinqa.python_eval import (
        MAX_NEW_TOKENS, SYSTEM_PYTHON, python_conversation
    )
    from convfinqa.tuned_eval import split_conversations

    cfg = files["configs/baseline.json"].json()
    if variant not in ("e0", "e3"):
        raise ValueError(f"variant must be 'e0' or 'e3', not {variant!r}")
    n_examples = int(variant[1:])
    if n_examples == 0 and seed != 0:
        raise ValueError(
            "a variant with no examples has no example set: use seed 0"
        )
    if bounds not in ("free", "bounded"):
        raise ValueError(f"bounds must be 'free' or 'bounded', not {bounds!r}")

        split,
        list(deps["train_val_split"].jsonl("val.jsonl")),

            c["id"]: c
            for c in deps["train_val_split"].jsonl("train_fit.jsonl")
        }

    start, done = time.perf_counter(), 0
    with open(out / "predictions.jsonl", "w") as f:
        def sink(row):
            nonlocal done
            f.write(json.dumps({
                k: v for k, v in row.items() if k != "seconds"
            }) + "\n")
            f.flush()
            done += 1
            if done % 50 == 0:

                    f"{done} turns, {time.perf_counter() - start:.0f} s",
                    flush=True
                )

        generate_with_grammar(
            cfg, [python_conversation(c) for c in convs],
            [python_conversation(c) for c in examples],
            system=SYSTEM_PYTHON, grammar=python_grammar(bounds == "bounded"),
            max_new_tokens=MAX_NEW_TOKENS, mode=mode, sink=sink,
```

## The same prompt, with the grammar off and on {#sec-constrained-results}

Validation turns only (@sec-formatting), predicted history, greedy, one attempt, an invalid answer counts as wrong. Each
row is one prompt run twice, with the same decoding and the grammar on or off, on the same turns, so the difference is
paired. The grammar is the unbounded one (`free`); @sec-constrained-bounds compares it with the bounded one.

## What the grammar cannot fix {#sec-constrained-gap}

How far does an untuned model with the best prompt and a grammar get towards the fine-tuned one? The grammar only
repairs syntax, so there is a ceiling: an untuned model whose every invalid answer became a correct one would score its
accuracy plus its invalid rate.

```{python}
#HEAVY
tuned_off = off_ci["fine-tuned DSL"]["accuracy"]
tuned_on = on_ci["fine-tuned DSL"]["accuracy"]
gap = {}
for k in ["untuned DSL", "untuned Python"]:
    start = off_ci[k]["accuracy"]
    gap[k] = {
        "ceiling": start + off_sum[k]["invalid_rate"],
        "with grammar": on_ci[k]["accuracy"],
        "total gap": tuned_off - start,
        "closed": (on_ci[k]["accuracy"] - start) / (tuned_off - start),
    }
    assert gap[k]["ceiling"] < tuned_off, k
vs_tuned = paired_difference(
    on["fine-tuned DSL"], on["untuned DSL"]
)
assert vs_tuned["low"] > 0
pd.DataFrame([
    {
        "system": k,
        "no grammar": pct(off_ci[k]["accuracy"]),
        "ceiling": pct(g["ceiling"]),
        "with grammar": pct(g["with grammar"]),

        "share of the gap closed": pct(g["closed"]),
    }
    for k, g in gap.items()
]).set_index("system")
```

For the DSL, the ceiling is `{python} pct(gap["untuned DSL"]["ceiling"])`, below the fine-tuned model's
`{python} pct(tuned_off)`; for Python it is `{python} pct(gap["untuned Python"]["ceiling"])`. Even a grammar that made
every invalid answer correct could not reach the fine-tuned model. The grammar closes
`{python} pct(gap["untuned DSL"]["closed"])` of the gap for the DSL and `{python} pct(gap["untuned Python"]["closed"])`
for Python (the Python gap is measured against the same fine-tuned DSL model). With the grammar on both, the fine-tuned
DSL model is `{python} pts(vs_tuned["difference"])` points ahead of the untuned one (interval
[`{python} pts(vs_tuned["low"])`, `{python} pts(vs_tuned["high"])`]).

What is left is choosing the operations and the numbers. In the error kinds of @sec-baseline, the untuned DSL with the
grammar still has `{python} on_sum["untuned DSL"]["by_kind"]["wrong_operations"]` turns with different operations from
the gold program, `{python} on_sum["untuned DSL"]["by_kind"]["wrong_numbers"]` with the same operations and different
numbers, and `{python} on_sum["untuned DSL"]["by_kind"]["wrong_answer"]` with the same shape and a different answer.
The fine-tuned model has `{python} on_sum["fine-tuned DSL"]["by_kind"]["wrong_operations"]`,
`{python} on_sum["fine-tuned DSL"]["by_kind"]["wrong_numbers"]` and
`{python} on_sum["fine-tuned DSL"]["by_kind"]["wrong_answer"]`. The classifier compares the operations first, so a
turn with the wrong operations and the wrong numbers is counted once, as wrong operations. What fine-tuning changes
most is the first of these.

## Description or enforcement? {#sec-constrained-2x2}

The plain system message names no syntax rules for the DSL; the description message spells them out. They are two
ways to tell the model the syntax, and the grammar is a third. The 2×2 below, with three examples, separates them.

```{python}
#HEAVY
CELLS = {
    ("plain", "off"): get("scores_untuned_val_e3p_0_pred"),
```

The grammar helps with either message: `{python} pts(enforce["plain"]["difference"])` points with the plain one
(interval [`{python} pts(enforce["plain"]["low"])`, `{python} pts(enforce["plain"]["high"])`]) and
`{python} pts(enforce["description"]["difference"])` with the description
([`{python} pts(enforce["description"]["low"])`, `{python} pts(enforce["description"]["high"])`]). The two intervals
overlap, so this run does not show that the gain differs. Changing the plain message for the description changes
accuracy by `{python} pts(describe["off"]["difference"])` points without a grammar
([`{python} pts(describe["off"]["low"])`, `{python} pts(describe["off"]["high"])`]) and by
`{python} pts(describe["on"]["difference"])` with one
([`{python} pts(describe["on"]["low"])`, `{python} pts(describe["on"]["high"])`]). With the description the grammar

turns, against `{python} cell_sum[("plain", "on")]["by_kind"]["bad_reference"]` with the plain message), which no grammar of
this kind rules out. So the description does not make the grammar redundant, and the grammar does not make the
description worth having: with the grammar on, the description is the lower of the two.

## Without examples {#sec-constrained-e0}

The three-example prompts show the format twice over: in the examples, and in the model's own earlier answers when
they are valid. The prompt with no examples (`e0p`, the training prompt) shows it in neither. Without a grammar,
the model with its own history is at the floor (@sec-python-untuned).

```{python}
#HEAVY
E0 = {
    "grammar off, predicted history": get("scores_untuned_val_e0p_0_pred"),
    "grammar on, predicted history": get(
        "scores_constrained_untuned_val_e0p_0_pred_free"
    ),
    "grammar off, gold history": get("scores_untuned_val_e0p_0_gold"),

e0 = {k: list(h.jsonl("scores.jsonl")) for k, h in E0.items()}
e0_sum = {k: h.json("summary.json") for k, h in E0.items()}

follow_up = lambda rows: [r for r in rows if r["turn"] > 0]
acc = lambda rows: sum(r["correct"] for r in rows) / len(rows)
e0_gain = paired_difference(
    e0["grammar on, predicted history"], e0["grammar off, predicted history"]

off_first = acc(first_turn(e0["grammar off, predicted history"]))
on_first = acc(first_turn(e0["grammar on, predicted history"]))
on_follow = acc(follow_up(e0["grammar on, predicted history"]))
gold_follow = acc(follow_up(e0["grammar off, gold history"]))

assert on_first > 10 * off_first
assert on_follow < gold_follow
pd.DataFrame([
    {
        "run": k,
        "all turns": pct(acc(rows)),
        "first turns": pct(acc(first_turn(rows))),
        "follow-ups": pct(acc(follow_up(rows))),
        "invalid": pct(e0_sum[k]["invalid_rate"]),
        "hit the limit": pct(e0_sum[k]["truncated"] / n_val),
    }
    for k, rows in e0.items()
]).set_index("run")
```

With the grammar, the untuned model with no examples goes from `{python} pct(acc(e0["grammar off, predicted history"]))`
to `{python} pct(acc(e0["grammar on, predicted history"]))`, a change of `{python} pts(e0_gain["difference"])` points
(interval [`{python} pts(e0_gain["low"])`, `{python} pts(e0_gain["high"])`]). The first turn has no history, so its
change is the effect of the grammar alone: from `{python} pct(off_first)` to `{python} pct(on_first)`. The grammar is
the only thing here that tells the model what an answer looks like, and it is enough for some answers.

The follow-up turns reach `{python} pct(on_follow)` with the grammar and the model's own history. With the gold
history and no grammar they reach `{python} pct(gold_follow)`. The two runs differ in the history (valid but mostly
wrong, against correct) and in the grammar, so this does not separate what each contributes.

Many of these answers do not stop: `{python} pct(e0_sum["grammar on, predicted history"]["truncated"] / n_val)` of the
turns hit the generation limit, with digits that keep coming. That is what the bounded grammar is for.

## Bounding the numbers {#sec-constrained-bounds}

A grammar guarantees syntax, not termination. The bounded variant allows at most the digits that the gold programs
use (ten before the point, four after it), so a run of digits must end.

```{python}
    "untuned DSL, no examples": (
        get("scores_constrained_untuned_val_e0p_0_pred_free"),
        get("scores_constrained_untuned_val_e0p_0_pred_bounded"),
    ),

free = {k: list(v[0].jsonl("scores.jsonl")) for k, v in BOUNDS.items()}
bounded = {k: list(v[1].jsonl("scores.jsonl")) for k, v in BOUNDS.items()}
free_sum = {k: v[0].json("summary.json") for k, v in BOUNDS.items()}
bounded_sum = {k: v[1].json("summary.json") for k, v in BOUNDS.items()}
bound_gain = {k: paired_difference(bounded[k], free[k]) for k in BOUNDS}
for k in BOUNDS:
    assert not bound_gain[k]["excludes_zero"], k
    assert (
        bounded_sum[k]["truncated"] < free_sum[k]["truncated"]
    ), k
assert bounded_sum["untuned DSL, no examples"]["truncated"] == 0
pd.DataFrame([
    {
        "run": k,
        "free": pct(free_sum[k]["accuracy"]),
        "bounded": pct(bounded_sum[k]["accuracy"]),
        "bounded − free (points)": pts(bound_gain[k]["difference"]),
        "95% paired interval":
            f"[{pts(bound_gain[k]['low'])}, {pts(bound_gain[k]['high'])}]",
        "hit the limit, free": free_sum[k]["truncated"],
        "hit the limit, bounded": bounded_sum[k]["truncated"],
    }
    for k in BOUNDS
]).set_index("run")
```

The bounded grammar cuts the turns that hit the limit
(`{python} free_sum["untuned DSL, no examples"]["truncated"]` to
`{python} bounded_sum["untuned DSL, no examples"]["truncated"]` with no examples), and accuracy does not change: the
paired intervals include zero in both rows. So the unbounded grammar was not hiding accuracy, and the numbers in the
rest of the chapter are those of the unbounded one. The bounded grammar is the safer one to use when a run must end, and costs nothing here.

## Discussion {#sec-constrained-discussion}

A grammar fixes the form and leaves the content, and the results above are what that looks like. Two pieces of
related work are worth comparing.

- **Format restrictions can hurt reasoning.** @tam2024speak compare language models restricted to
  structured output formats such as JSON or XML with free-form answers. They report a drop in reasoning ability under
  the restriction, larger for stricter formats. That concerns a model
  that reasons in the text it writes and is then made to write it in a format. Here the output is the program: there is
  no free text for the grammar to cut short, and the fine-tuned model does not change under the grammar. This
  chapter's runs do not test their claim.
- **FinQA's decoder was restricted too.** The program generator of the original FinQA model takes its
  output tokens from three sources: the tokens of the question and the retrieved facts (the numbers), the special
  tokens of the DSL, and tokens for the results of earlier steps. At inference time it also applies masks from the
  grammar of the DSL at every decoding step, to keep the program well formed [@chen2021finqa]. Its output space is
  narrower than that of the syntax grammar of this chapter, which lets any number be written. A grammar that restricts the numbers to those
of the page in the same way is not run in this book (@sec-other-things).

::: {.callout-tip title="Further reading"}
- @dong2024xgrammar describe `xgrammar`, the library used here.
- @tam2024speak study the effect of format restrictions on reasoning.
:::

## Summary

- A grammar sets the probability of every token it does not allow to zero and leaves the rest as the model had them.
  At the start of a DSL answer, `{python} len(step_ids["start of the answer"])` of
  `{python} f"{VOCAB:,}"` tokens remain.
- On validation turns with predicted history, the grammar takes the untuned DSL from
  `{python} pct(off_ci["untuned DSL"]["accuracy"])` to `{python} pct(on_ci["untuned DSL"]["accuracy"])` and untuned
  Python from `{python} pct(off_ci["untuned Python"]["accuracy"])` to `{python} pct(on_ci["untuned Python"]["accuracy"])`,
  and invalid answers nearly disappear. The fine-tuned model is unchanged
  (`{python} pct(off_ci["fine-tuned DSL"]["accuracy"])` to `{python} pct(on_ci["fine-tuned DSL"]["accuracy"])`).
- The gain is under half of the invalid output removed, and mostly on program turns. The grammar closes
  `{python} pct(gap["untuned DSL"]["closed"])` of the gap between the untuned and the fine-tuned model; the ceiling is
  below the fine-tuned accuracy.
- The grammar helps with the plain and the description prompt alike, and, with no examples, takes the model from the
  floor to `{python} pct(acc(e0["grammar on, predicted history"]))`.
- The bounded number rule removes the runaway digits and does not change accuracy.
- These are validation results. The final results do not repeat the grammar comparison on the development data.
