12  Training with LoRA

You will learn:

  • the settings of the training run, and why each one has the value it has;
  • how the work is organised: a short check on a small model, then the main run;
  • what the run did to the loss, and what the trained adapter looks like: the size and rank of its updates, and what they do to the model’s view of the gold answers.

Chapter 8 showed what one training step does, and Chapter 9 what a LoRA adapter is. This chapter puts the two to work: it trains an adapter for Qwen3-4B-Instruct-2507 on the training conversations, formatted as in Chapter 10. The machinery has nothing new in it. The work is in choosing the settings, and in checking while the run goes that it does what we think it does.

12.1 The data

The run trains on train-fit, and the validation split is what it is checked against.

There are 2,731 training conversations and 306 validation conversations. Every conversation is one training example: the system message, then the questions and answers in turn, with the loss counted on the answers only (Chapter 8, “Which tokens count”). The development split is not used here, not even to choose a checkpoint. Everything that is decided in this chapter is decided on the validation split.

12.2 The configuration settings

The settings of every run are in one file, configs/train.json: the ones all runs share, and a few entries for each named run. A light artifact, train_config_{run}, merges the two for one run, so a run’s settings are a file that can be read, and a change to one run’s entry does not change what the others were built from.

Code 
@artifact("train_config_{run}", files=["configs/train.json"])
def build_train_config(out, deps, files, *, run: str):
    """Combine the base train config with the run-specific settings.

    The combined config is written to the output directory as "config.json".
    
    Args:
        out: The output directory for the combined config.
        deps: Dependencies (unused here).
        files: Dictionary of input files, keyed by their paths.
            Here the only key used is "configs/train.json".
        run: The name of the run to get the specific settings for.
    """
    import json

    from convfinqa.train_config import run_config

    cfg = run_config(files["configs/train.json"].json(), run)
    (out / "config.json").write_text(json.dumps(cfg, indent=2))

Most of these were explained in the chapters before this one. The reasons, in order:

LoRA. Rank 16, alpha 32 (so the update is scaled by \(\alpha / r =\) 2), dropout 0.05 on the adapter’s input, and an adapter on every linear layer of the decoder (all-linear): the seven matrices of Chapter 9. The model’s own weights stay in bf16 and the adapter, which is what trains, in fp32. The rank is a guess at how much freedom the task needs, and Chapter 17 returns to it.

The learning rate and its schedule. A peak of 2e-4, reached after a linear warmup of 11 steps and then falling along half a cosine wave to zero by step 342 (Chapter 8, “The learning-rate schedule”). The rate is 10 times that of the full fine-tuning run of Chapter 8 (2e-5): the adapter starts at zero and has to travel to be useful, and it has far fewer weights to move.

The batch. Micro-batches of 4 conversations, with 4 of them accumulated into each update, so each update uses 16 conversations. With 2,731 conversations that makes 171 steps an epoch, and 342 in the 2 epochs. Gradient clipping at a norm of 1.0 guards against one odd batch.

Weight decay. It is zero. Weight decay pulls every trainable weight a little towards zero at each step, a brake on weights that would otherwise keep growing. It earns its keep when a large network trains for a long time on much data. Here the adapter starts at zero, trains for about 342 steps, and the checkpoint is chosen by its validation loss, which already guards against training for too long. Pulling the adapter towards zero would also pull the model towards where it started, which the learning rate and the choice of checkpoint control more directly. If the validation loss turns up while the training loss still falls, this is the first setting to revisit.

Length and memory. Conversations are cut at 3,584 tokens (the longest in the data is 3,460, Chapter 2, so nothing is cut). Gradient checkpointing is on, as in Chapter 8, because the activations of such long sequences would otherwise take more memory than the weights do. The process is capped at 80 GB of the GPU’s memory, which the desktop shares.

12.3 The two runs

Code 
# the smoke run changes the model and the length of the run,
# and nothing about how the model learns
assert {k for k in cfg if cfg[k] != smoke[k]} \
    == {"model", "max_steps", "eval_every"}
assert cfg["weight_decay"] == 0

The smoke run trains Qwen/Qwen2.5-0.5B-Instruct for 50 steps with the same recipe. It takes minutes, and is there to check the whole chain (the data, the training, the choice of the best checkpoint, the numbers recorded) before the main run spends hours. Nothing is concluded from its accuracy, and the book does not build it by default: python -m convfinqa.artifacts build check_lora_smoke_0 runs it. It changes only the model, the number of steps and how often the validation loss is measured. The main run trains Qwen/Qwen3-4B-Instruct-2507 for the full 342 steps.

Both runs measure the loss on the validation conversations before the first step and then every 50 steps (every 10 for the smoke run), and at the end. Only the checkpoint with the lowest validation loss is kept, as the adapter that the rest of the book uses.

The validation loss is the mean over answer tokens, so that every answer token weighs the same, as in the training loss and in the loss of the untuned model measured in Chapter 7. (The Trainer’s own evaluation averages the mean losses of the conversations instead, which gives a short conversation the weight of a long one; the training code corrects for that, so that the first validation loss can be compared with the untuned model’s.)

Two artifacts carry a run, both named by the run (smoke, main) and the seed of the training. lora_{run}_{seed} trains the adapter and writes it with the loss history. check_lora_{run}_{seed} loads the adapter and measures its accuracy on a small sample of validation turns. The training itself is convfinqa.finetune.train_lora: the chapter holds the settings and the calls, the package the logic.

Code 
@artifact(
    "lora_{run}_{seed}",
    deps=["train_val_split", "train_config_{run}"],
    heavy=True,
)
def build_lora(out, deps, *, run: str, seed: int):
    """
    Build and train the LoRA adapter for a given run and seed.

    Args:
        out : The output directory for the adapter and training state.
        deps : The dependencies, including the training configuration
            and data splits.
        run : The run identifier, e.g., "smoke" or "main".
        seed : The random seed for training.
    """
    import json

    from convfinqa.finetune import train_lora

    cfg = deps[f"train_config_{run}"].json("config.json")
    fit = list(deps["train_val_split"].jsonl("train_fit.jsonl"))
    val = list(deps["train_val_split"].jsonl("val.jsonl"))
    result = train_lora(cfg, fit, val, out, seed)
    history = {k: result.pop(k) for k in ("log_history", "max_steps")}
    (out / "trainer_state.json").write_text(json.dumps(history))
    (out / "metrics.json").write_text(json.dumps(result, indent=2))


@artifact(
    "check_lora_{run}_{seed}",
    deps=[
        "lora_{run}_{seed}", "train_config_{run}",
        "train_val_split", "eval_turns",
    ],
    heavy=True,
)
def build_check_lora(out, deps, *, run: str, seed: int):
    """
    Evaluate the LoRA adapter trained by `build_lora`.

    Does not call `build_lora` itself; the results are loaded
    from the dependencies.

    Args:
        out : The output directory for the check results.
        deps : The dependencies, including the adapter, training
            configuration, and data splits.
        run : The run identifier, e.g., "smoke" or "main".
        seed : The random seed for training.
    """
    import json

    from convfinqa.finetune import check_adapter

    cfg = deps[f"train_config_{run}"].json("config.json")
    result = check_adapter(
        cfg,
        deps[f"lora_{run}_{seed}"].path / "adapter",
        list(deps["train_val_split"].jsonl("val.jsonl")),
        list(deps["eval_turns"].jsonl("val_turns.jsonl")),
    )
    (out / "summary.json").write_text(json.dumps(result["summary"], indent=2))
    (out / "scores.jsonl").write_text(
        "".join(json.dumps(s) + "\n" for s in result["scores"])
    )
    (out / "predictions.jsonl").write_text(
        "".join(json.dumps(p) + "\n" for p in result["predictions"])
    )

The validation loss starts at 2.2062, which is the untuned model’s loss of Chapter 7, now measured through the training code, so the two agree. By step 50 it has fallen to 0.052, 42-fold. It keeps falling at every check up to step 250, where it reaches 0.0357. The first check alone covers over 90% of the whole fall. The last two checks are within 0.3% of it: the loss has levelled off while the learning rate falls along the tail of the cosine (Figure 8.3). The kept adapter is the one from step 250, of the 342 steps the run took. The loss is not rising again, so the run shows no sign of overfitting, and the weight decay of zero was not a problem.

12.5 A quick check of the adapter

The validation loss says how surprised the model is by the gold answers. It does not say what the model does when it writes its own. check_lora_main_0 generates the answers for a sample of validation turns with the kept adapter, with the same machinery as the untuned baseline of Chapter 11, but with the gold history in the prompt, and the training prompt: the system message of Chapter 10, with no examples. 12.6 What the adapter changed

The adapter is a set of pairs \((A, B)\), and each pair stands for an update \(\Delta W = \frac{\alpha}{r} B A\) to one weight matrix. We can look at the updates themselves. The first artifact reads the saved adapter and, for every one of the adapted matrices, the size of the update (its Frobenius norm, the square root of the sum of its squared entries) relative to the size of the weight matrix it modifies, and the singular values of the update (explained below).

Code 
#HEAVY
# Generate the adapter-to-base-weight analysis
# For each layer and matrix kind, compute the ratio of the update's norm
# to the base weight's norm. Also compute the share of the update's squared norm
# captured by each singular value.
@artifact(
    "adapter_analysis_{run}_{seed}",
    deps=["lora_{run}_{seed}", "train_config_{run}"],
)
def build_adapter_analysis(out, deps, *, run: str, seed: int):
    import json

    from convfinqa.adapter_stats import adapter_update_stats, base_weight_norms

    cfg = deps[f"train_config_{run}"].json("config.json")
    stats = adapter_update_stats(deps[f"lora_{run}_{seed}"].path / "adapter")
    base = base_weight_norms(cfg["model"])
    for m in stats["matrices"]:
        m["relative_norm"] = m["norm"] / base[(m["layer"], m["module"])]
    (out / "stats.json").write_text(json.dumps(stats))


stats = get("adapter_analysis_main_0").json("stats.json")
mods, n_layers = stats["modules"], stats["layers"]
relative = np.zeros((n_layers, len(mods)))
for m in stats["matrices"]:
    relative[m["layer"], mods.index(m["module"])] = m["relative_norm"]
sq_sv = np.array([m["singular_values"] for m in stats["matrices"]]) ** 2
sq_share = sq_sv / sq_sv.sum(1, keepdims=True)
cumulative = sq_share.cumsum(1).mean(0)

The rank \(r =\) 16 is used: the largest singular value holds on average 56% of an update’s squared norm, and it takes 7 of the 16 directions to hold 90%.

NoteUnder the hood: what the singular values say

A matrix of rank 16 is a sum of 16 rank-1 matrices. A rank-1 matrix is a column times a row, \(\sigma\, u v^\top\): it reads the input along one direction (the row \(v^\top\)), scales it by \(\sigma\), and writes the result along one direction of the output (the column \(u\)). This is the usual form \(U \Sigma V^\top\) of the singular value decomposition written out column by column: \(\Delta W = \sum_i \sigma_i u_i v_i^\top\), with \(\sigma_1 \ge \sigma_2 \ge \dots\) the singular values and the \(u_i\) (and the \(v_i\)) perpendicular to each other. The squared size of the matrix (the squared Frobenius norm) is the sum of the squared singular values, which is why the figure shows squared norms: each singular value takes its share.

Keeping only the \(k\) largest terms of the sum gives a matrix of rank \(k\), and it is the closest matrix of rank \(k\) to the original: no other comes nearer (the Eckart–Young theorem). The squared distance is the squared singular values that were dropped. So the curve of Figure 12.3 can be read the other way round: the best stand-in of rank 7 for an update of rank 16 would be off by 9% of the update’s squared norm, on average over the matrices.

Two cautions. The stand-in is closest in the weights, not necessarily in what the model does: a small term can still matter. And it is not what an adapter of rank 7 trained from scratch would find, because that one is fitted to the task, not cut from this one. The rank sweep later in the book tests that directly.

NoteFurther reading

These sizes are the sizes of the update, not of its effect: a small change in the right place can change the output a lot, and a large one in a direction the data never uses changes nothing. The next section looks at the effect directly, on the tokens themselves. Hu et al. (2022) found that a very small rank was often enough for the update of a language model, which is the other side of the same question.

12.7 What the adapter changed in the model’s view

The effect on the model is easier to see in the gold tokens’ log-probabilities. The artifact adapter_logprobs_{run}_{seed} computes them for the twenty validation conversations that Chapter 7 studied, once with the base model and once with the adapter attached, in the training format and with the gold history.

# Training with LoRA {#sec-training}

**You will learn:**

- the settings of the training run, and why each one has the value it has;
- how the work is organised: a short check on a small model, then the main run;
- what the run did to the loss, and what the trained adapter looks like: the size and rank of its updates, and what
  they do to the model's view of the gold answers.

@sec-fine-tuning showed what one training step does, and @sec-lora what a LoRA adapter is. This chapter puts the two
to work: it trains an adapter for `Qwen3-4B-Instruct-2507` on the training conversations, formatted as in
@sec-formatting. The machinery has nothing new in it. The work is in choosing the settings, and in checking while the
run goes that it does what we think it does.

## The data

The run trains on **[train-fit](901_glossary.qmd#gloss-train-fit)**, and the **validation** split is what it is checked against.

There are `{python} f"{n_fit:,}"` training conversations and `{python} n_val` validation conversations. Every
conversation is one training example: the system message, then the questions and answers in turn, with the loss counted

## The configuration settings

The settings of every run are in one file, `configs/train.json`: the ones all runs share, and a few entries for each
named run. A light artifact, `train_config_{run}`, merges the two for one run, so a run's settings are a file that can be
read, and a change to one run's entry does not change what the others were built from.

```{python}
@artifact("train_config_{run}", files=["configs/train.json"])
def build_train_config(out, deps, files, *, run: str):
    """Combine the base train config with the run-specific settings.

    The combined config is written to the output directory as "config.json".
    
    Args:
        out: The output directory for the combined config.
        deps: Dependencies (unused here).
        files: Dictionary of input files, keyed by their paths.
            Here the only key used is "configs/train.json".
        run: The name of the run to get the specific settings for.
    """
    import json

    from convfinqa.train_config import run_config

    cfg = run_config(files["configs/train.json"].json(), run)
    (out / "config.json").write_text(json.dumps(cfg, indent=2))
```

The settings of the main run that decide how it behaves (the smoke run of the next section differs in three of them):

Most of these were explained in the chapters before this one. The reasons, in order:

**LoRA.** Rank `{python} cfg["lora"]["r"]`, alpha `{python} cfg["lora"]["alpha"]` (so the update is scaled by
$\alpha / r =$ `{python} f"{cfg['lora']['alpha'] / cfg['lora']['r']:g}"`), dropout `{python} cfg["lora"]["dropout"]`
on the adapter's input, and an adapter on every linear layer of the decoder (`{python} cfg["lora"]["target_modules"]`):
the seven matrices of @sec-lora. The model's own weights stay in bf16 and the adapter, which is what trains, in fp32.
The rank is a guess at how much freedom the task needs, and @sec-rank-sweep returns to it.

**The learning rate and its schedule.** A peak of `{python} sci(cfg["lr"])`, reached after a linear warmup of
`{python} warmup` steps and then falling along half a cosine wave to zero by step `{python} steps`
(@sec-fine-tuning, "The learning-rate schedule"). The rate is `{python} f"{cfg['lr'] / full_lr:.0f}"` times that of the full
fine-tuning run of @sec-fine-tuning (`{python} sci(full_lr)`): the adapter starts at zero and has to travel to be
useful, and it has far fewer weights to move.

**The batch.** Micro-batches of `{python} cfg["micro_batch"]` conversations, with
`{python} cfg["accumulation"]` of them accumulated into each update, so each update uses
`{python} cfg["micro_batch"] * cfg["accumulation"]` conversations. With `{python} f"{n_fit:,}"` conversations that makes `{python} steps_per_epoch` steps an epoch, and
`{python} steps` in the `{python} cfg["epochs"]` epochs. Gradient clipping at a norm of
`{python} cfg["max_grad_norm"]` guards against one odd batch.

**Weight decay.** It is zero. Weight decay pulls every trainable weight a little towards zero at each step, a brake on
weights that would otherwise keep growing. It earns its keep when a large network trains for a long time on much data.
Here the adapter starts at zero, trains for about `{python} steps` steps, and the checkpoint is chosen by its validation
loss, which already guards against training for too long. Pulling the adapter towards zero would also pull the model
towards where it started, which the learning rate and the choice of checkpoint control more directly. If the
validation loss turns up while the training loss still falls, this is the first setting to revisit.

**Length and memory.** Conversations are cut at `{python} f"{cfg['max_length']:,}"` tokens (the longest in the data is
`{python} f"{lengths['longest']:,}"`, @sec-convfinqa, so nothing is cut). Gradient checkpointing is on, as in @sec-fine-tuning, because the
activations of such long sequences would otherwise take more memory than the weights do. The process is capped at
`{python} cfg["memory_cap_gb"]` GB of the GPU's memory, which the desktop shares.

## The two runs

```{python}
# the smoke run changes the model and the length of the run,
# and nothing about how the model learns
assert {k for k in cfg if cfg[k] != smoke[k]} \
    == {"model", "max_steps", "eval_every"}
assert cfg["weight_decay"] == 0
```

The **[smoke run](901_glossary.qmd#gloss-smoke-run)** trains `{python} smoke["model"]` for `{python} smoke["max_steps"]` steps with the same recipe. It
takes minutes, and is there to check the whole chain (the data, the training, the choice of the best checkpoint, the
numbers recorded) before the main run spends hours. Nothing is concluded from its accuracy, and the book does not build
it by default: `python -m convfinqa.artifacts build check_lora_smoke_0` runs it. It changes only the
model, the number of steps and how often the validation loss is measured. The **[main run](901_glossary.qmd#gloss-main-run)** trains
`{python} cfg["model"]` for the full `{python} steps` steps.

Both runs measure the loss on the validation conversations before the first step and then every
`{python} cfg["eval_every"]` steps (every `{python} smoke["eval_every"]` for the smoke run), and at the end. Only the
checkpoint with the lowest validation loss is kept, as the adapter that the rest of the book uses.

The validation loss is the mean over answer tokens, so that every answer token weighs the same, as in the training loss
and in the loss of the untuned model measured in @sec-probing. (The Trainer's own evaluation averages the mean losses
of the conversations instead, which gives a short conversation the weight of a long one; the training code corrects
for that, so that the first validation loss can be compared with the untuned model's.)

Two artifacts carry a run, both named by the run (`smoke`, `main`) and the seed of the training.
`lora_{run}_{seed}` trains the adapter and writes it with the loss history. `check_lora_{run}_{seed}` loads the adapter
and measures its accuracy on a small sample of validation turns. The training itself is `convfinqa.finetune.train_lora`:
the chapter holds the settings and the calls, the package the logic.

```{python}
@artifact(
    "lora_{run}_{seed}",
    deps=["train_val_split", "train_config_{run}"],
    heavy=True,
)
def build_lora(out, deps, *, run: str, seed: int):
    """
    Build and train the LoRA adapter for a given run and seed.

    Args:
        out : The output directory for the adapter and training state.
        deps : The dependencies, including the training configuration
            and data splits.
        run : The run identifier, e.g., "smoke" or "main".
        seed : The random seed for training.
    """
    import json

    from convfinqa.finetune import train_lora

    cfg = deps[f"train_config_{run}"].json("config.json")
    fit = list(deps["train_val_split"].jsonl("train_fit.jsonl"))
    val = list(deps["train_val_split"].jsonl("val.jsonl"))
    result = train_lora(cfg, fit, val, out, seed)
    history = {k: result.pop(k) for k in ("log_history", "max_steps")}
    (out / "trainer_state.json").write_text(json.dumps(history))
    (out / "metrics.json").write_text(json.dumps(result, indent=2))


@artifact(
    "check_lora_{run}_{seed}",
    deps=[
        "lora_{run}_{seed}", "train_config_{run}",
        "train_val_split", "eval_turns",
    ],
    heavy=True,
)
def build_check_lora(out, deps, *, run: str, seed: int):
    """
    Evaluate the LoRA adapter trained by `build_lora`.

    Does not call `build_lora` itself; the results are loaded
    from the dependencies.

    Args:
        out : The output directory for the check results.
        deps : The dependencies, including the adapter, training
            configuration, and data splits.
        run : The run identifier, e.g., "smoke" or "main".
        seed : The random seed for training.
    """
    import json

    from convfinqa.finetune import check_adapter

    cfg = deps[f"train_config_{run}"].json("config.json")
    result = check_adapter(
        cfg,
        deps[f"lora_{run}_{seed}"].path / "adapter",
        list(deps["train_val_split"].jsonl("val.jsonl")),
        list(deps["eval_turns"].jsonl("val_turns.jsonl")),
    )
    (out / "summary.json").write_text(json.dumps(result["summary"], indent=2))
    (out / "scores.jsonl").write_text(
        "".join(json.dumps(s) + "\n" for s in result["scores"])
    )
    (out / "predictions.jsonl").write_text(
        "".join(json.dumps(p) + "\n" for p in result["predictions"])
    )
```

## What the adapter changed

The adapter is a set of pairs $(A, B)$, and each pair stands for an update $\Delta W = \frac{\alpha}{r} B A$ to one
weight matrix. We can look at the updates themselves. The first artifact reads the saved adapter and, for every one
of the adapted matrices, the size of the update (its Frobenius norm, the square root of the sum of its squared entries)
relative to the size of the weight matrix it modifies, and the singular values of the update (explained below).

```{python}
#HEAVY
# Generate the adapter-to-base-weight analysis
# For each layer and matrix kind, compute the ratio of the update's norm
# to the base weight's norm. Also compute the share of the update's squared norm
# captured by each singular value.
@artifact(
    "adapter_analysis_{run}_{seed}",
    deps=["lora_{run}_{seed}", "train_config_{run}"],
)
def build_adapter_analysis(out, deps, *, run: str, seed: int):
    import json

    from convfinqa.adapter_stats import adapter_update_stats, base_weight_norms

    cfg = deps[f"train_config_{run}"].json("config.json")
    stats = adapter_update_stats(deps[f"lora_{run}_{seed}"].path / "adapter")
    base = base_weight_norms(cfg["model"])
    for m in stats["matrices"]:
        m["relative_norm"] = m["norm"] / base[(m["layer"], m["module"])]
    (out / "stats.json").write_text(json.dumps(stats))


stats = get("adapter_analysis_main_0").json("stats.json")
mods, n_layers = stats["modules"], stats["layers"]
relative = np.zeros((n_layers, len(mods)))
for m in stats["matrices"]:
    relative[m["layer"], mods.index(m["module"])] = m["relative_norm"]
sq_sv = np.array([m["singular_values"] for m in stats["matrices"]]) ** 2
sq_share = sq_sv / sq_sv.sum(1, keepdims=True)
cumulative = sq_share.cumsum(1).mean(0)
K = 7

# the update is small next to the weight, and does not sit on one direction
assert relative.max() < 0.02
assert sq_share[:, 0].mean() < 0.75 and cumulative[7] > 0.85
```

The rank $r =$ `{python} stats["r"]` is used: the largest singular value holds on average
`{python} f"{sq_share[:, 0].mean():.0%}"` of an update's squared norm, and it takes `{python} int(np.argmax(cumulative > 0.9)) + 1`
of the `{python} stats["r"]` directions to hold 90%.

::: {.callout-note title="Under the hood: what the singular values say"}
A matrix of rank 16 is a sum of 16 **rank-1 matrices**. A rank-1 matrix is a column times a row, $\sigma\, u v^\top$:
it reads the input along one direction (the row $v^\top$), scales it by $\sigma$, and writes the result along one
direction of the output (the column $u$). This is the usual form $U \Sigma V^\top$ of the singular value decomposition
written out column by column: $\Delta W = \sum_i \sigma_i u_i v_i^\top$, with $\sigma_1 \ge \sigma_2 \ge \dots$ the
**[singular values](901_glossary.qmd#gloss-singular-values)** and the $u_i$ (and the $v_i$) perpendicular to each other. The squared size of the matrix (the
squared Frobenius norm) is the sum of the squared singular values, which is why the figure shows squared norms: each
singular value takes its share.

Keeping only the $k$ largest terms of the sum gives a matrix of rank $k$, and it is the closest matrix of rank $k$ to the
original: no other comes nearer (the Eckart–Young theorem). The squared distance is the squared singular values that
were dropped. So the curve of @fig-adapter-rank can be read the other way round: the best stand-in of rank
`{python} K` for an update of rank `{python} stats["r"]` would be off by
`{python} f"{1 - cumulative[K - 1]:.0%}"` of the update's squared norm, on average over the matrices.

Two cautions. The stand-in is closest in the weights, not necessarily in what the model does: a small term can still
matter. And it is not what an adapter of rank `{python} K` trained from scratch would find, because that one is fitted to the
task, not cut from this one. The rank sweep later in the book tests that directly.
:::

::: {.callout-note title="Further reading"}
These sizes are the sizes of the update, not of its effect: a small change in the right place can change the output
a lot, and a large one in a direction the data never uses changes nothing. The next section looks at the effect
directly, on the tokens themselves. @hu2022lora found that a very small rank was often enough for the update of a language model, which is
the other side of the same question.
:::

## What the adapter changed in the model's view

The effect on the model is easier to see in the gold tokens' log-probabilities. The artifact
`adapter_logprobs_{run}_{seed}` computes them for the twenty validation conversations that @sec-probing studied, once
with the base model and once with the adapter attached, in the training format and with the gold history.

before and after fine-tuning, with red marking surprisal. After fine-tuning, none of its tokens has a trace of red.
