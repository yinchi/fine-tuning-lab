14  DSL or Python?

  • Show All Code

You will learn:

  • why the book’s program language is a question worth testing, and what a fair test of it looks like;
  • how a ConvFinQA program is written as Python, and how Python written by a model is run without trusting it;
  • how much of the DSL’s difficulty the untuned model already avoids when it writes Python, and whether the difference survives fine-tuning.

Every program in this book so far is in the ConvFinQA DSL: subtract(5, 3), divide(#0, 3). The DSL is small and exact, and it is also unlike anything the model saw in pretraining. A model trained on a great deal of code might write Python, which it knows, more reliably than a language invented for one dataset. The ConvFinQA paper (Chen et al. 2022) reports that GPT-3 did better with ordinary math notation than with the DSL, and program-of-thought prompting (Chen et al. 2023) writes Python for the same reason. This chapter tests it on our model.

The test is on the untuned model first. The question is how well the model already knows Python, and an adapter trained to write one format or the other would answer a different question. A second stage trains an adapter for Python, and compares it with the DSL adapter of Chapter 12, because a difference between the untuned models might not survive fine-tuning. That stage was planned to run only if the untuned model did clearly better in Python, and it did. Every number in this chapter is measured on the validation split; the development split is not used.

14.1 Python as an output format

A program in the DSL is a list of steps. The Python form keeps the arithmetic and writes it the way a person would: a step that is used once is put inside the expression that uses it, a step that is used more than once is named, and the answer is assigned to ans. convfinqa.dsl.python_format.to_python does the translation, and it keeps the structure of the program exactly, with parentheses where it needs them, so that the operations are the same and in the same order.

Code 
import pandas as pd

from convfinqa.artifacts import artifact, get
from convfinqa.data.tables import turn_rows
from convfinqa.dsl import executor, python_format

train_fit = list(get("train_val_split").jsonl("train_fit.jsonl"))
programs = [r["program"] for r in turn_rows(train_fit)]
translated = [python_format.to_python(p) for p in programs]
same_answer = [
    python_format.try_execute_python(code)[0] == executor.try_execute(p)[0]
    for p, code in zip(programs, translated)
]
named = [p for p, code in zip(programs, translated) if "\n" in code]
assert all(same_answer)
# naming a step is the exception
assert len(named) < 0.01 * len(programs)

14.2 Running Python written by a model

A model asked for “a valid Python program” may write anything. Running that with exec would run whatever it wrote. Instead, python_format.execute_python parses the code with ast and walks the tree itself. It accepts assignments; arithmetic and comparisons on numbers; names that were assigned; and the calls round, abs, min, max and sum. All numbers are floats, so a huge power overflows and does not hang. The answer is the value of ans, rounded to five places as in the DSL, or yes or no for a comparison.

Code that is valid Python but outside this list, such as a function definition, an import, a loop or math.sqrt, is not run, and it is reported as its own kind of invalid output, outside the subset. The limit of the evaluator is then visible in the results, and is not mistaken for a mistake of the model.

14.3 The prompt

The DSL prompts of Chapter 11 describe the language. The Python prompt has three rules and nothing else, so that it measures what the model already knows: a valid Python program, numbers that appear on the page, and the answer assigned to ans. It says nothing about the structure of the program and nothing about the syntax.

Code 
from convfinqa.python_eval import MAX_NEW_TOKENS, SYSTEM_PYTHON
from convfinqa.tuned_eval import MAX_NEW_TOKENS as DSL_MAX_NEW_TOKENS

Answer with a valid Python program. Use only numbers that appear on the page. Assign the final answer to ans.

Most answers in the examples are short: 70% of the gold programs of the training conversations are a number or a single operation, which Python writes as ans = a - b. The style of the translation is therefore part of what the examples teach, and the results with examples are partly a result about that style.

A fence around the code counts as invalid, as in the DSL, and the fence rate is reported next to the accuracy. Free-form Python is longer than a DSL program, so the generation limit is 256 tokens and not 96, and the share of generations that reach it is reported.

14.4 The code

python_untuned_{split}_{variant}_{seed}_{mode} generates the answers with the untuned model; the variant e0 has no examples and e3 has three from example set seed. scores_python_untuned_… is light: it executes and scores the outputs. The scores have the fields of the DSL scores, so everything that compares systems works on them.

Code 
@artifact(
    "python_untuned_{split}_{variant}_{seed}_{mode}",
    deps=["train_val_split", "eval_turns", "example_sets"],
    files=["configs/baseline.json"],
    heavy=True,
)
def build_python_untuned(
    out, deps, files, *, split: str, variant: str, seed: int, mode: str
):
    """Generate the untuned model's Python answer for every turn of a split.

    Args:
        out: Output directory; `predictions.jsonl` is written to it.
        deps: The conversations and the example sets.
        files: `configs/baseline.json` (the model).
        split: `val`, or `dev` once `configs/FROZEN` exists.
        variant: `e0` (no examples) or `e3` (three examples).
        seed: The example set; 0 for `e0`.
        mode: `gold` or `pred`, the history of the earlier turns.
    """
    import json
    import time

    from convfinqa.python_eval import generate_untuned_python
    from convfinqa.tuned_eval import split_conversations

    cfg = files["configs/baseline.json"].json()
    if variant not in ("e0", "e3"):
        raise ValueError(f"variant must be 'e0' or 'e3', not {variant!r}")
    n_examples = int(variant[1:])
    if n_examples == 0 and seed != 0:
        raise ValueError(
            "a variant with no examples has no example set: use seed 0"
        )
    convs = split_conversations(
        split,
        list(deps["train_val_split"].jsonl("val.jsonl")),
        list(deps["eval_turns"].jsonl("dev.jsonl")),
    )
    examples = []
    if n_examples:
        wanted = deps["example_sets"].json(
            "sets.json"
        )["sets"][str(seed)][:n_examples]
        pool = {
            c["id"]: c
            for c in deps["train_val_split"].jsonl("train_fit.jsonl")
        }
        examples = [pool[i] for i in wanted]
    start, done = time.perf_counter(), 0
    with open(out / "predictions.jsonl", "w") as f:
        def sink(row):
            nonlocal done
            f.write(json.dumps({
                k: v for k, v in row.items() if k != "seconds"
            }) + "\n")
            f.flush()
            done += 1
            if done % 50 == 0:
                print(
                    f"{done} turns, {time.perf_counter() - start:.0f} s",
                    flush=True
                )

        generate_untuned_python(cfg, convs, examples, mode, sink)
    print(f"done: {done} turns in {time.perf_counter() - start:.0f} s")


@artifact(
    "scores_python_untuned_{split}_{variant}_{seed}_{mode}",
    deps=["python_untuned_{split}_{variant}_{seed}_{mode}", "eval_turns"],
)
def build_scores_python_untuned(
    out, deps, *, split: str, variant: str, seed: int, mode: str
):
    """Execute and score the outputs of `python_untuned_…`."""
    import json

    from convfinqa.evaluate import summarize
    from convfinqa.python_eval import score_python_rows

    rows = list(
        deps[f"python_untuned_{split}_{variant}_{seed}_{mode}"]
        .jsonl("predictions.jsonl")
    )
    turns = list(deps["eval_turns"].jsonl(f"{split}_turns.jsonl"))
    scores = score_python_rows(rows, turns)
    (out / "scores.jsonl").write_text(
        "".join(json.dumps(s) + "\n" for s in scores)
    )
    (out / "summary.json").write_text(
        json.dumps(summarize(scores), indent=2)
    )

14.9 Numbers from the page, and the scale

The prompt asks for numbers that appear on the page. Two checks from Section 13.6.2 show whether the outputs follow it, here for Python. The literal check compares the numbers written in the code with those of the translated gold program, as text and as values, and tests whether each comes from the page. Python has no named constants, so a program that needs 100 writes 100; the numbers the DSL’s named constants stand for (1 to 9, the powers of ten up to 10^9, and -1) count as allowed. 14.10 Summary

  • A ConvFinQA program written as Python is the same computation: all 9,979 training programs give the same answer in both, and only 15 need a named step. Python written by a model is run by a whitelist evaluator, never by exec.
  • Untuned, with three examples, Python is +7.4 points ahead of the DSL with predicted history and +8.6 with gold history, and both intervals exclude zero. The lead is about as large as the difference in invalid output, so much of it may be the untuned model not yet writing the DSL.
  • After fine-tuning the formats are not different on validation data: the leads are -0.3 and +0.8 points, and both intervals include zero.
  • Without examples, all of the gain from the gold history is on the follow-up turns, where the earlier answers show the format. With examples, the Python lead is on the follow-ups too: on first turns the DSL is slightly ahead.
  • Checked on the outputs that run, the adapters write only numbers from the page and are rarely off by a power of ten; the untuned model with examples is not, so these checks separate tuned from untuned and not Python from the DSL.
  • Python is not carried forward: the fine-tuned Python rows stay on the validation data, and the later stages use the DSL.

# DSL or Python? {#sec-python-format}

**You will learn:**

- why the book's program language is a question worth testing, and what a fair test of it looks like;
- how a ConvFinQA program is written as Python, and how Python written by a model is run without trusting it;
- how much of the DSL's difficulty the untuned model already avoids when it writes Python, and whether the difference
  survives fine-tuning.

Every program in this book so far is in the ConvFinQA DSL: `subtract(5, 3), divide(#0, 3)`. The DSL is small and
exact, and it is also unlike anything the model saw in pretraining. A model trained on a great deal of code might
write Python, which it knows, more reliably than a language invented for one dataset. The ConvFinQA paper
[@chen2022convfinqa] reports that GPT-3 did better with ordinary math notation than with the DSL, and
program-of-thought prompting [@chen2022program] writes Python for the same reason. This chapter tests it on our model.

The test is on the **untuned** model first. The question is how well the model already knows Python, and an adapter
trained to write one format or the other would answer a different question. A second stage trains an adapter for
Python, and compares it with the DSL adapter of @sec-training, because a difference between the untuned models might not
survive fine-tuning. That stage was planned to run only if the untuned model did clearly better in Python, and it did.
Every number in this chapter is measured on the validation split; the development split is not used.

## Python as an output format

A program in the DSL is a list of steps. The Python form keeps the arithmetic and writes it the way a person would:
a step that is used once is put inside the expression that uses it, a step that is used more than once is named, and
the answer is assigned to `ans`. `convfinqa.dsl.python_format.to_python` does the translation, and it keeps the
structure of the program exactly, with parentheses where it needs them, so that the operations are the same and in the
same order.

```{python}
    "DSL": examples,
    "Python": [python_format.to_python(p).replace("\n", "; ") for p in examples],
    "answer": [executor.execute(p) for p in examples],
}).set_index("DSL")
```

A percentage such as `4.02%` is written `4.02 / 100`, which keeps the digits that are on the page. The constants
`const_100` and `const_m1` become the numbers `100` and `-1`. Of the `{python} f"{len(programs):,}"` gold programs in the
training conversations, every one gives the same answer in Python as in the DSL, and only `{python} len(named)` need a
named step.

## Running Python written by a model

A model asked for "a valid Python program" may write anything. Running that with `exec` would run whatever it wrote.
Instead, `python_format.execute_python` parses the code with `ast` and walks the tree itself. It accepts assignments;
arithmetic and comparisons on numbers; names that were assigned; and the calls `round`, `abs`, `min`, `max` and `sum`.
All numbers are floats, so a huge power overflows and does not hang. The answer is the value of `ans`, rounded to five
places as in the DSL, or `yes` or `no` for a comparison.

Code that is valid Python but outside this list, such as a function definition, an import, a loop or `math.sqrt`, is
not run, and it is reported as its own kind of invalid output, **outside the subset**. The limit of the evaluator is
then visible in the results, and is not mistaken for a mistake of the model.

```{python}

    "ans = 3 > 2",
```

## The prompt

The DSL prompts of @sec-baseline describe the language. The Python prompt has three rules and nothing else, so that it
measures what the model already knows: a valid Python program, numbers that appear on the page, and the answer
assigned to `ans`. It says nothing about the structure of the program and nothing about the syntax.

```{python}

from convfinqa.tuned_eval import MAX_NEW_TOKENS as DSL_MAX_NEW_TOKENS

```

There are two variants. With no examples the prompt is these rules alone. With examples, the three conversations of
example set 0 are shown first, as in @sec-baseline, with their gold programs translated by `to_python`. This is the
chat for the first question of a validation conversation, with the long texts cut:

Most answers in the examples are short: `{python} f"{100 * single:.0f}"`% of the gold programs of the training conversations

part of what the examples teach, and the results with examples are partly a result about that style.

A fence around the code counts as invalid, as in the DSL, and the fence rate is reported next to the accuracy. Free-form
Python is longer than a DSL program, so the generation limit is `{python} MAX_NEW_TOKENS` tokens and not
`{python} DSL_MAX_NEW_TOKENS`, and the share of generations that reach it is reported.

## The code

`python_untuned_{split}_{variant}_{seed}_{mode}` generates the answers with the untuned model; the variant `e0` has no
examples and `e3` has three from example set `seed`. `scores_python_untuned_…` is light: it executes and scores
the outputs. The scores have the fields of the DSL scores, so everything that compares systems works on them.

```{python}
@artifact(
    "python_untuned_{split}_{variant}_{seed}_{mode}",
    deps=["train_val_split", "eval_turns", "example_sets"],
    files=["configs/baseline.json"],
    heavy=True,
)
def build_python_untuned(
    out, deps, files, *, split: str, variant: str, seed: int, mode: str
):
    """Generate the untuned model's Python answer for every turn of a split.

    Args:
        out: Output directory; `predictions.jsonl` is written to it.
        deps: The conversations and the example sets.
        files: `configs/baseline.json` (the model).
        split: `val`, or `dev` once `configs/FROZEN` exists.
        variant: `e0` (no examples) or `e3` (three examples).
        seed: The example set; 0 for `e0`.
        mode: `gold` or `pred`, the history of the earlier turns.
    """
    import json
    import time

    from convfinqa.python_eval import generate_untuned_python
    from convfinqa.tuned_eval import split_conversations

    cfg = files["configs/baseline.json"].json()
    if variant not in ("e0", "e3"):
        raise ValueError(f"variant must be 'e0' or 'e3', not {variant!r}")
    n_examples = int(variant[1:])
    if n_examples == 0 and seed != 0:
        raise ValueError(
            "a variant with no examples has no example set: use seed 0"
        )
    convs = split_conversations(
        split,
        list(deps["train_val_split"].jsonl("val.jsonl")),
        list(deps["eval_turns"].jsonl("dev.jsonl")),
    )
    examples = []
    if n_examples:
        wanted = deps["example_sets"].json(
            "sets.json"
        )["sets"][str(seed)][:n_examples]
        pool = {
            c["id"]: c
            for c in deps["train_val_split"].jsonl("train_fit.jsonl")
        }
        examples = [pool[i] for i in wanted]
    start, done = time.perf_counter(), 0
    with open(out / "predictions.jsonl", "w") as f:
        def sink(row):
            nonlocal done
            f.write(json.dumps({
                k: v for k, v in row.items() if k != "seconds"
            }) + "\n")
            f.flush()
            done += 1
            if done % 50 == 0:
                print(
                    f"{done} turns, {time.perf_counter() - start:.0f} s",
                    flush=True
                )

        generate_untuned_python(cfg, convs, examples, mode, sink)
    print(f"done: {done} turns in {time.perf_counter() - start:.0f} s")


@artifact(
    "scores_python_untuned_{split}_{variant}_{seed}_{mode}",
    deps=["python_untuned_{split}_{variant}_{seed}_{mode}", "eval_turns"],
)
def build_scores_python_untuned(
    out, deps, *, split: str, variant: str, seed: int, mode: str
):
    """Execute and score the outputs of `python_untuned_…`."""
    import json

    from convfinqa.evaluate import summarize
    from convfinqa.python_eval import score_python_rows

    rows = list(
        deps[f"python_untuned_{split}_{variant}_{seed}_{mode}"]
        .jsonl("predictions.jsonl")
    )
    turns = list(deps["eval_turns"].jsonl(f"{split}_turns.jsonl"))
    scores = score_python_rows(rows, turns)
    (out / "scores.jsonl").write_text(
        "".join(json.dumps(s) + "\n" for s in scores)
    )
    (out / "summary.json").write_text(
        json.dumps(summarize(scores), indent=2)
    )
```

### First turns and follow-ups

The first turn of a conversation has no history, so the two history modes give it the same prompt. The follow-up
turns are where they differ.

```{python}
#HEAVY
def split_first(scores):
    """Accuracy of the first turn of each conversation, and of the others."""
    first_turn = {}
    for s in scores:
        first_turn[s["id"]] = min(first_turn.get(s["id"], s["turn"]), s["turn"])
    groups = {True: [], False: []}
    for s in scores:
        groups[s["turn"] == first_turn[s["id"]]].append(s["correct"])
    return {
        "first": sum(groups[True]) / len(groups[True]),
        "later": sum(groups[False]) / len(groups[False]),
        "n_first": len(groups[True]),
        "n_later": len(groups[False]),
    }


split = {
    (fmt, v, m): split_first(sc[(v, m)])
    for fmt, sc in [("DSL", dsl_scores), ("Python", py_scores)]
    for v in ("e0", "e3")
    for m in ("pred", "gold")
}
pd.DataFrame(
    [
        {
            "output": fmt,
            "examples": "none" if v == "e0" else "three",
            "history": m,
            "first turn": pct(r["first"]),
            "follow-ups": pct(r["later"]),
        }
        for (fmt, v, m), r in split.items()
    ]
).set_index(["output", "examples", "history"])
```

## Is a Python adapter worth training?

The rule set before the runs was to train one only if untuned Python is clearly ahead of untuned DSL. It is: in
every condition where either format works, the paired interval of the lead excludes zero. That is a statement about
the untuned model, and what the model does after fine-tuning is a separate question.

```{python}
#HEAVY

    k: dsl_summary[k]["invalid_rate"] - py_summary[k]["invalid_rate"]
    for k in [("e3", "pred"), ("e3", "gold")]
}
# most of the lead is invalid outputs that the DSL runs produce and the
# Python runs do not
assert all(fewer_invalid[k] > 0.8 * lead[k]["difference"] for k in fewer_invalid)
```

With examples, the DSL runs produce `{python} pts(fewer_invalid[("e3", "pred")])` and
`{python} pts(fewer_invalid[("e3", "gold")])` points more invalid outputs than the Python runs (predicted and gold
history), against leads of `{python} pts(lead[("e3", "pred")]["difference"])` and
`{python} pts(lead[("e3", "gold")]["difference"])`. The lead is about as large as the difference in invalid output, so it
may be largely the untuned model failing to write the DSL, which tuning removes: an adapter for the DSL writes a valid
program on essentially every turn of the validation data (@sec-evaluating-errors). If a lead remains after tuning, it is a lead in the reasoning, and the only way to see it is
to train.

The next step is one adapter for Python with the hyperparameters of the DSL adapter,
scored on the validation data in both history modes. It reaches the development data only if its lead over the DSL
adapter has a paired interval that excludes zero.

## The Python adapter

The adapter for Python is trained like the DSL adapter of @sec-fine-tuning, with the same settings: the run `python`
of `configs/train.json` has the same entries as `main`, so `train_config_python` is the same configuration. Only the
data differ. Every gold program is translated by `to_python`, and the system message is the Python prompt, so the
adapter is trained on the prompt it is evaluated with, and the loss counts the Python answers only.
`convfinqa.python_finetune` holds the data and the call; the training is `finetune.train_lora`.

```{python}
@artifact(
    "python_lora_{seed}",
    deps=["train_val_split", "train_config_python"],
    heavy=True,
)
def build_python_lora(out, deps, *, seed: int):
    """Train the Python adapter on the train-fit split.

    Args:
        out: The output directory for the adapter and training state.
        deps: The conversations and the `python` run's settings.
        seed: The random seed for training.
    """
    import json

    from convfinqa.python_finetune import train_lora_python

    cfg = deps["train_config_python"].json("config.json")
    fit = list(deps["train_val_split"].jsonl("train_fit.jsonl"))
    val = list(deps["train_val_split"].jsonl("val.jsonl"))
    result = train_lora_python(cfg, fit, val, out, seed)
    history = {k: result.pop(k) for k in ("log_history", "max_steps")}
    (out / "trainer_state.json").write_text(json.dumps(history))
    (out / "metrics.json").write_text(json.dumps(result, indent=2))


@artifact(
    "python_tuned_{split}_{seed}_{mode}",
    deps=[
        "python_lora_{seed}", "train_config_python",
        "train_val_split", "eval_turns",
    ],
    heavy=True,
)
def build_python_tuned(out, deps, *, split: str, seed: int, mode: str):
    """Generate the Python adapter's answer for every turn of a split.

    Args:
        out: Output directory; `predictions.jsonl` is written to it.
        deps: The adapter, its settings and the conversations.
        split: `val`, or `dev` once `configs/FROZEN` exists.
        seed: The training seed of the adapter.
        mode: `gold` or `pred`, the history of the earlier turns.
    """
    import json
    import time

    from convfinqa.python_finetune import generate_tuned_python
    from convfinqa.tuned_eval import split_conversations

    cfg = deps["train_config_python"].json("config.json")
    convs = split_conversations(
        split,
        list(deps["train_val_split"].jsonl("val.jsonl")),
        list(deps["eval_turns"].jsonl("dev.jsonl")),
    )
    start, done = time.perf_counter(), 0
    with open(out / "predictions.jsonl", "w") as f:
        def sink(row):
            nonlocal done
            f.write(json.dumps({
                k: v for k, v in row.items() if k != "seconds"
            }) + "\n")
            f.flush()
            done += 1
            if done % 50 == 0:
                print(
                    f"{done} turns, {time.perf_counter() - start:.0f} s",
                    flush=True
                )

        generate_tuned_python(
            cfg, deps[f"python_lora_{seed}"].path / "adapter",
            convs, mode, sink,
        )
    print(f"done: {done} turns in {time.perf_counter() - start:.0f} s")


@artifact(
    "scores_python_tuned_{split}_{seed}_{mode}",
    deps=["python_tuned_{split}_{seed}_{mode}", "eval_turns"],
)
def build_scores_python_tuned(out, deps, *, split: str, seed: int, mode: str):
    """Execute and score the outputs of `python_tuned_…`."""
    import json

    from convfinqa.evaluate import summarize
    from convfinqa.python_eval import score_python_rows

    rows = list(
        deps[f"python_tuned_{split}_{seed}_{mode}"].jsonl("predictions.jsonl")
    )
    turns = list(deps["eval_turns"].jsonl(f"{split}_turns.jsonl"))
    scores = score_python_rows(rows, turns)
    (out / "scores.jsonl").write_text(
        "".join(json.dumps(s) + "\n" for s in scores)
    )
    (out / "summary.json").write_text(
        json.dumps(summarize(scores), indent=2)
    )
```

## Numbers from the page, and the scale {#sec-python-numbers}

The prompt asks for numbers that appear on the page. Two checks from @sec-evaluating-errors show whether the
outputs follow it, here for Python. The literal check compares the numbers written in the code with those of the
translated gold program, as text and as values, and tests whether each comes from the page. Python has no named
constants, so a program that needs `100` writes `100`; the numbers the DSL's named constants stand for (1 to 9, the
powers of ten up to 10^9, and -1) count as allowed. The scale check runs the code and looks for an answer that is the
gold answer times, or over, a power of ten. `convfinqa.python_checks` holds both.

```{python}

    "checks_python_untuned_{split}_{variant}_{seed}_{mode}",

)
```

Every number in the translated gold programs is on the page or is a constant, so the check can pass. The adapters
pass it on every turn that runs: they write only numbers from the page, so their mistakes are not invented numbers. The untuned model with examples fails it on `{python} pct(ungrounded["untuned, three examples, predicted"])` of
its turns that run with predicted history and `{python} pct(ungrounded["untuned, three examples, gold"])` with the gold
history. The untuned model is also off by a power of ten on `{python} off_scale["untuned, three examples, predicted"]`
and `{python} off_scale["untuned, three examples, gold"]` turns, against
`{python} off_scale["fine-tuned, predicted"]` and `{python} off_scale["fine-tuned, gold"]` for the adapters. The test for
numbers from the page is weak, since a page holds many numbers, so it can show that a model invents numbers, and not
that it picks the right ones.

## Summary

- A ConvFinQA program written as Python is the same computation: all `{python} f"{len(programs):,}"` training programs give
  the same answer in both, and only `{python} len(named)` need a named step. Python written by a model is run by a
  whitelist evaluator, never by `exec`.
- Untuned, with three examples, Python is `{python} pts(lead[("e3", "pred")]["difference"])` points ahead of the DSL with
  predicted history and `{python} pts(lead[("e3", "gold")]["difference"])` with gold history, and both intervals exclude
  zero. The lead is about as large as the difference in invalid output, so much of it may be the untuned model not yet
  writing the DSL.
- After fine-tuning the formats are not different on validation data: the leads are
  `{python} pts(tuned_lead["pred"]["difference"])` and `{python} pts(tuned_lead["gold"]["difference"])` points, and both
  intervals include zero.
- Without examples, all of the gain from the gold history is on the follow-up turns, where the earlier answers show the
  format. With examples, the Python lead is on the follow-ups too: on first turns the DSL is slightly ahead.
- Checked on the outputs that run, the adapters write only numbers from the page and are rarely off by a power of ten;
  the untuned model with examples is not, so these checks separate tuned from untuned and not Python from the DSL.
- Python is not carried forward: the fine-tuned Python rows stay on the validation data, and the later stages use the DSL.
