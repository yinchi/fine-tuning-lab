13.1 Two histories

A conversation is a sequence of questions, and each answer can use the earlier ones: “and what is that as a percentage?” is a question about the answer before it. When the model answers turn \(k\), the prompt holds the turns before it, and there are two ways to fill in the model’s side of them.

  • Gold history. The earlier answers are the gold programs, as in training. This is called teacher forcing: the model is never shown its own mistakes. Each turn is an independent question with the right context, so the score says how well the model answers when everything before it was right.
  • Predicted history. The earlier answers are the model’s own outputs, exactly as generated, valid or not. This is how the model would be used: a mistake at turn 2 is in the prompt at turn 3. It is the headline mode of the book.

Gold-history accuracy is what predicted-history accuracy would be if no earlier mistake carried over, and the gap between the two, turn by turn, shows how far errors compound. No conversation and no turn is dropped in either mode: a turn that follows a wrong answer is still scored.

13.2 The policy for invalid outputs

Decoding is greedy, with one attempt per turn, and an output that is not a valid program, or that does not execute, counts as wrong. The denominator is every turn. This is what the official ConvFinQA evaluation does, and what the published numbers we compare with assume. In predicted history, an invalid output stays in the history as it was generated. The share of invalid outputs is reported next to the accuracy, by cause, because it says where the errors are: not being able to write the language, or writing it wrongly.

13.3 The code

Two artifacts evaluate a run. Both are named by the split, the run, the seed of the training and the history mode. tuned_{split}_{run}_{seed}_{mode} loads the adapter of Chapter 12 and writes one output per turn, with the training prompt and no examples; like the baseline’s, it refuses dev until the freeze file exists. scores_tuned_… is light: it executes and scores the outputs. The generation is convfinqa.tuned_eval.generate_tuned.

Code 
from convfinqa.artifacts import artifact, get


@artifact(
    "tuned_{split}_{run}_{seed}_{mode}",
    deps=[
        "train_val_split", "eval_turns",
        "lora_{run}_{seed}", "train_config_{run}",
    ],
    heavy=True,
)
def build_tuned(out, deps, *, split: str, run: str, seed: int, mode: str):
    """Generate the fine-tuned model's output for every turn of a split.

    Args:
        out: Output directory; `predictions.jsonl` is written to it.
        deps: The adapter, its settings and the conversations.
        split: `val`, or `dev` once `configs/FROZEN` exists.
        run: The training run (`main`).
        seed: The seed of the training.
        mode: `gold` or `pred`, the history of the earlier turns.
    """
    import json
    import time

    from convfinqa.tuned_eval import generate_tuned, split_conversations

    cfg = deps[f"train_config_{run}"].json("config.json")
    convs = split_conversations(
        split,
        list(deps["train_val_split"].jsonl("val.jsonl")),
        list(deps["eval_turns"].jsonl("dev.jsonl")),
    )
    start, done = time.perf_counter(), 0
    with open(out / "predictions.jsonl", "w") as f:
        def sink(row):
            nonlocal done
            f.write(json.dumps({
                k: v for k, v in row.items() if k != "seconds"
            }) + "\n")   # timing is not an output
            f.flush()
            done += 1
            if done % 50 == 0:
                print(
                    f"{done} turns, {time.perf_counter() - start:.0f} s",
                    flush=True
                )

        generate_tuned(
            cfg, deps[f"lora_{run}_{seed}"].path / "adapter",
            convs, mode, sink
        )
    print(f"done: {done} turns in {time.perf_counter() - start:.0f} s")


@artifact(
    "scores_tuned_{split}_{run}_{seed}_{mode}",
    deps=["tuned_{split}_{run}_{seed}_{mode}", "eval_turns"],
)
def build_scores_tuned(out, deps, *, split: str, run: str, seed: int, mode: str):
    """Execute and score the outputs of `tuned_{split}_{run}_{seed}_{mode}`."""
    import json

    from convfinqa.evaluate import score_rows, summarize
    from convfinqa.program_match import add_program_match

    rows = list(
        deps[f"tuned_{split}_{run}_{seed}_{mode}"].jsonl("predictions.jsonl")
    )
    turns = list(deps["eval_turns"].jsonl(f"{split}_turns.jsonl"))
    scores = add_program_match(score_rows(rows, turns), rows, turns)
    (out / "scores.jsonl").write_text(
        "".join(json.dumps(s) + "\n" for s in scores)
    )
    (out / "summary.json").write_text(
        json.dumps(summarize(scores), indent=2)
    )

13.4 Results on the validation split

The fine-tuned model uses the adapter that Chapter 12 kept (the checkpoint with the lowest validation loss, seed 0). We run this model using the same prompt as in training: the one-line system message and no examples, denoted e0p in Chapter 11. This is compared against the untuned model using both e0p and e3p, which adds three examples to the system prompt: the former shows what fine-tuning changed, while the latter shows what is left for fine-tuning to add after the prompt has done its best. 13.5 Beyond execution accuracy

Execution accuracy asks only whether the number is right. Two further measures look at the program itself and at the numbers it is written with, and the error analysis below uses both.

13.5.1 Program accuracy

Execution accuracy asks whether the program gives the right number. Program accuracy asks whether it is the right program, by the rule of the official ConvFinQA script. The two programs are compared as expressions, so the operands of an add or a multiply may come in either order, and a calculation may be split over the steps in another way. The arguments are compared as exact text: the numbers must be copied off the page as they are, so 2.70 is not 2.7, and 17% is not 0.17. A program that reaches the right answer from other numbers is not the gold program either.

Because the gold program gives the gold answer, a turn that is right by program is right by execution too. The interesting counts are the other way round: how much program accuracy loses against execution accuracy, and what the turns in between look like.

13.5.2 Where the numbers come from

Program accuracy compares whole programs. The literal check looks only at the numbers a program is written with, and so it works for any output format. For each turn it asks three things: are the numbers the same as the gold program’s as text, are they the same as values (2.70 is 2.7, 17% is 0.17, const_100 is 100), and is every number that is not a named constant from the page, as text. The gap between the first two is formatting; the third says whether the numbers were copied, not made up. The scale check is separate: it asks whether the answer is the gold answer times a power of ten.

13.6.3 How close was the right token?

A wrong program is a sequence of token choices. The gold program and the model’s are the same text up to the first token where they differ, so up to there the model chose as the gold program does, and its distribution at that position is the one it wrote its own token from. Its rank for the gold token there (1 is the most probable token), and the ratio of the gold token’s probability to the probability of the token it wrote, say whether the right answer was a near miss or far away. divergence_{split}_{run}_{seed} scores the wrong turns of the predicted-history run with the same prompts, in one forward pass each.

13.7 Variations on the setup

13.7.1 Does a prompt still help the tuned model?

The adapter was trained on the one-line prompt and no examples. Fine-tuning and prompting are two routes to the same end, and nothing says that they cannot be taken together: the same three examples that did the most for the untuned model (e3p) can be put in front of the tuned one. If they help, the two routes add up. If they do not, the adapter has already taken up what the examples were teaching, or the examples are now an input unlike any that it was trained on, and get in the way.

prompted_tuned_{split}_{run}_{seed}_{variant}_{shots}_{mode} asks the tuned model with a prompt variant of Chapter 11: variant names the variant and shots the example set, as in the baseline’s artifacts. The examples come from the training conversations, as they did there.

13.7.2 Does merging the adapter change the answers?

13.7.3 Does extra compute at inference help?

Everything above is one greedy attempt per turn. The cheapest way to spend more generations on a turn is self-consistency (Wang et al. (2023)): sample several programs at a temperature, drop those that do not run, and take the answer most of them agree on; the history takes the first program with that answer. The temperature is only there to make the samples differ, since greedy decoding would give the same program every time. The number of samples and the temperature are in configs/extra_compute.json. The question is whether five generations per turn beat one, so the row reports its cost in generations and tokens, which do not depend on the machine, next to its accuracy. It is a separate row and never enters the headline.

## Two histories

A conversation is a sequence of questions, and each answer can use the earlier ones: "and what is that as a
percentage?" is a question about the answer before it. When the model answers turn $k$, the prompt holds the turns
before it, and there are two ways to fill in the model's side of them.

- **Gold history.** The earlier answers are the gold programs, as in training. This is called *teacher forcing*: the
  model is never shown its own mistakes. Each turn is an independent question with the right context, so the score
  says how well the model answers when everything before it was right.
- **Predicted history.** The earlier answers are the model's own outputs, exactly as generated, valid or not. This is
  how the model would be used: a mistake at turn 2 is in the prompt at turn 3. It is the **headline** mode of the book.

Gold-history accuracy is what predicted-history accuracy would be if no earlier mistake carried over, and the gap
between the two, turn by turn, shows how far errors compound. No conversation and no turn is dropped in either mode:
a turn that follows a wrong answer is still scored.

## The policy for invalid outputs

Decoding is greedy, with **one attempt** per turn, and an output that is not a valid program, or that does not
execute, **counts as wrong**. The denominator is every turn. This is what the official ConvFinQA evaluation does, and
what the published numbers we compare with assume. In predicted history, an [invalid output](901_glossary.qmd#gloss-invalid-output) stays in the history as it
was generated. The share of invalid outputs is reported next to the accuracy, by cause, because it says where the
errors are: not being able to write the language, or writing it wrongly.

## Beyond execution accuracy

Execution accuracy asks only whether the number is right. Two further measures look at the program itself and at the
numbers it is written with, and the error analysis below uses both.

### Program accuracy

Execution accuracy asks whether the program gives the right number. **[Program accuracy](901_glossary.qmd#gloss-program-accuracy)** asks whether it is the right
program, by the rule of the official ConvFinQA script. The two programs are compared as expressions, so the operands of
an `add` or a `multiply` may come in either order, and a calculation may be split over the steps in another way. The
arguments are compared as exact text: the numbers must be copied off the page as they are, so `2.70` is not `2.7`, and
`17%` is not `0.17`. A program that reaches the right answer from other numbers is not the gold program either.

Because the gold program gives the gold answer, a turn that is right by program is right by execution too. The
interesting counts are the other way round: how much program accuracy loses against execution accuracy, and what the
turns in between look like.

### Where the numbers come from

Program accuracy compares whole programs. The **[literal check](901_glossary.qmd#gloss-literal-check)** looks only at the numbers a program is written with,
and so it works for any output format. For each turn it asks three things: are the numbers the same as the gold
program's *as text*, are they the same *as values* (`2.70` is `2.7`, `17%` is `0.17`, `const_100` is `100`), and is
every number that is not a named constant *from the page*, as text. The gap between the first two is formatting;
the third says whether the numbers were copied, not made up. The **[scale check](901_glossary.qmd#gloss-scale-check)** is separate: it asks whether the answer
is the gold answer times a power of ten.

### What the fine-tuned model gets wrong {#sec-evaluating-errors}

subtraction were reversed; a number is not from the page; the program has the same operations as the gold with other
numbers (or another number was copied where a number was asked for); it has other operations; or none of these.

### How close was the right token? {#sec-evaluating-close}

A wrong program is a sequence of token choices. The gold program and the model's are the same text up to the first
token where they differ, so up to there the model chose as the gold program does, and its distribution at that
position is the one it wrote its own token from. Its *rank* for the gold token there (1 is the most probable token), and the
*ratio* of the gold token's probability to the probability of the token it wrote, say whether the right answer
was a near miss or far away. `divergence_{split}_{run}_{seed}` scores the wrong turns of the predicted-history run
with the same prompts, in one forward pass each.

```{python}
@artifact(
    "divergence_{split}_{run}_{seed}",
    deps=[
        "train_val_split", "eval_turns",
        "lora_{run}_{seed}", "train_config_{run}",

        "scores_tuned_{split}_{run}_{seed}_pred",
    ],
    heavy=True,
)
def build_divergence(out, deps, *, split: str, run: str, seed: int):
    """Score the first token where each wrong program differs from the gold one.

    Args:
        out: Output directory; `divergences.jsonl` is written to it.
        deps: The adapter, the conversations and the predicted-history run.
        split: `val`, or `dev` once `configs/FROZEN` exists.
        run: The training run (`main`).
        seed: The seed of the training.
    """
    import json
```

## Variations on the setup

### Does a prompt still help the tuned model?

The adapter was trained on the one-line prompt and no examples. Fine-tuning and prompting are two routes to the same
end, and nothing says that they cannot be taken together: the same three examples that did the most for the untuned
model (`e3p`) can be put in front of the tuned one. If they help, the two routes add up. If they do not, the adapter
has already taken up what the examples were teaching, or the examples are now an input unlike any that it was trained
on, and get in the way.

`prompted_tuned_{split}_{run}_{seed}_{variant}_{shots}_{mode}` asks the tuned model with a prompt variant of
@sec-baseline: `variant` names the variant and `shots` the example set, as in the baseline's artifacts. The examples
come from the training conversations, as they did there.

### Does merging the adapter change the answers?

Everything above ran the adapter *separately*: a bf16 base model with the adapter's own weights in fp32, as in
training. A model that is deployed is usually *merged*, with the adapter's correction $\tfrac{\alpha}{r}BA$ added into
the base weights once, so that inference costs nothing extra. @sec-lora showed on a random adapter that this is the same
function in fp32 but not in bf16, where rounding the sum back to bf16 can change the model as much as the adapter did.
The trained adapter is smaller and has structure, so the effect may be smaller; here we measure it, on the same
validation turns, with the predicted history: the merge rounded into bf16 weights, and the whole model kept in fp32.

### Does extra compute at inference help?

Everything above is one greedy attempt per turn. The cheapest way to spend more generations on a turn is
*[self-consistency](901_glossary.qmd#gloss-self-consistency)* (@wang2023selfconsistency): sample several programs at a temperature, drop those that do not
run, and take the answer most of them agree on; the history takes the first program with that answer. The
temperature is only there to make the samples differ, since greedy decoding would give the same program every
time. The number of samples and the temperature are in `configs/extra_compute.json`. The question is whether five
generations per turn beat one, so the row reports its cost in generations and tokens, which do not depend on the
machine, next to its accuracy. It is a separate row and never enters the headline.

## What a turn costs

The systems of this chapter differ in what they cost as well as in what they get right. The cost is counted in
units that do not depend on the machine: generations per turn, prompt tokens (read once, in one pass) and generated
tokens (produced one at a time, so a generated token is dearer than a prompt token, and the table keeps them apart).
Seconds depend on the device and its settings, so they are left out.

```{python}
#HEAVY
COST = [
    ("untuned, e0p", "untuned_val_e0p_0_pred", "zero"),
    ("untuned, e3p", "untuned_val_e3p_0_pred", "base"),
    ("fine-tuned", "tuned_val_main_0_pred", "pred"),
    ("fine-tuned, e3p prompt", "prompted_tuned_val_main_0_e3p_0_pred", "shots"),
    ("fine-tuned, 5-sample vote", "extra_val_main_0_vote_full", "vote"),
]
cost_rows = {}
for label, name, key in COST:
    frame = pd.DataFrame(get(name).jsonl("predictions.jsonl"))
    cost_rows[key] = {
        "label": label,
        "generations": frame.get(
            "generations", pd.Series(1, index=frame.index)
        ).mean(),
        "prompt": frame.prompt_tokens.mean(),
        "generated": frame.new_tokens.mean(),
    }
assert cost_rows["pred"]["generated"] < cost_rows["zero"]["generated"]
assert cost_rows["shots"]["prompt"] > 3 * cost_rows["pred"]["prompt"]
assert cost_rows["vote"]["generations"] == 5
assert all(
    cost_rows["pred"][k] == min(c[k] for c in cost_rows.values())
    for k in ("prompt", "generated")
)
pd.DataFrame([
    {
        "system": c["label"],
        "accuracy": f"{ci[key]['accuracy']:.1%}",
        "generations per turn": f"{c['generations']:.0f}",
        "prompt tokens per turn": f"{c['prompt']:,.0f}",
        "generated tokens per turn": f"{c['generated']:.1f}",
    }
    for key, c in cost_rows.items()
]).set_index("system")
```

The fine-tuned model with its training prompt reads the fewest prompt tokens and writes the fewest generated tokens
of the five: it reads `{python} f"{cost_rows['pred']['prompt']:,.0f}"` prompt tokens (the table and the
conversation, with no examples) and writes `{python} f"{cost_rows['pred']['generated']:.1f}"`, where the untuned
model with the same prompt writes `{python} f"{cost_rows['zero']['generated']:.1f}"`. The three examples of `e3p`
make the prompt `{python} f"{cost_rows['shots']['prompt'] / cost_rows['pred']['prompt']:.1f}"` times as long, whether
the model is tuned or not, and the five-sample vote pays for five of everything. Fine-tuning moves the cost of the
examples from every call to the training run, which is paid once.
