The earlier chapters used one conversation. Here we look at a sample of them. The model is Qwen3-4B-Instruct-2507, untuned, and every example comes from the validation split, never from dev.

7.1 The validation split

train.json is the training file. We hold out a tenth of its conversations for tuning decisions (which prompt, which checkpoint) and train on the rest. The split is made by report page: several conversations are written from the same page, and if one were in training and its sibling in validation, the model could be graded on a page it had been trained on. Dev stays untouched, for the final numbers.

Code 
import pandas as pd

7.2 Asking the untuned model

We take a small random sample of validation conversations and ask the model for every turn. Each turn is a separate request with the gold history (the earlier answers are the dataset’s programs), so the requests are independent and each one measures a single turn. Decoding is greedy and the answer is judged exactly as generated: no cleaning, and an answer the executor rejects is wrong. That is the rule the headline evaluation will use.

We try two prompts. Zero-shot is the system prompt Answer with a program in the ConvFinQA DSL., the page and the question, and nothing else. Few-shot puts two complete conversations, with their gold programs, in front of the same request, drawn from train-fit.

These runs take a few minutes (they load the 4B model and generate every answer twice), so they are an artifact: built once in a subprocess, and loaded here. The same artifact holds the gold programs’ token probabilities that we read in the next section.

Code 
#HEAVY
@artifact("probe_val_sample", deps=["train_val_split"], heavy=True)
def build_probe_val_sample(out, deps):
    import json
    import random

    import torch
    from transformers import AutoModelForCausalLM, AutoTokenizer

    from convfinqa.probing import probe_sample

    name = "Qwen/Qwen3-4B-Instruct-2507"
    tok = AutoTokenizer.from_pretrained(name)
    model = AutoModelForCausalLM.from_pretrained(
        name, dtype=torch.bfloat16, device_map="cuda"
    ).eval()
    fit = list(deps["train_val_split"].jsonl("train_fit.jsonl"))
    val = list(deps["train_val_split"].jsonl("val.jsonl"))

The kinds, as probing.classify_output defines them:

  • code_fence: the answer is wrapped in a markdown fence, usually with invented syntax inside.
  • syntax, bad_number, unknown_operator: the executor could not read it. These are format failures: the model answered in some language, but not the DSL.
  • wrong_operations, wrong_numbers, wrong_answer: a valid program with the wrong answer. These are reasoning or reading failures: a different list of operations, different numbers picked from the page, or the right shape with the wrong value.

Examples shift the balance from the first group to the second: the model learns the format from two conversations, but picking the right cells and the right operation is a different skill. Fine-tuning has to teach both, and the invalid rate it removes is the easy part.

7.3 How surprised is the model by the gold program?

Generation shows what the model does. We can also ask how likely it finds the gold answer. One forward pass over the whole conversation gives, for every token, the probability the model assigned to it given everything before it. The negative log of that probability is the token’s surprisal, in nats (natural log). It is the surprisal of the gold token given the gold tokens before it (teacher forcing), with no comparison to what the model would have chosen. The cross-entropy loss fine-tuning minimizes is the mean surprisal over the answer tokens.

The surprise is in the DSL’s own words: the operator that opens a program, the ), between two steps, the (# of a reference to an earlier step. We can measure it across the sample, by kind of token:

Code 
def token_class(piece):
    text = piece.strip()
    if piece == "<|im_end|>":
        return "end of turn"
    if "#" in text:
        return "#k reference"
    if text.startswith(")") and "," in text:
        return "step separator"
    if text.replace("_", "").isalpha():
        return "operator / constant name"
    if text and all(ch.isdigit() or ch in ".%,-" for ch in text):
        return "number"
    return "bracket / other"

records = []
for row in surprisal:
    turn = 0
    for piece, lp in zip(row["tokens"], row["logprobs"]):
        records.append({
            "class": token_class(piece),
            "turn": min(turn, 4) + 1,
            "surprisal": -lp
        })
        turn += piece == "<|im_end|>"
tokens = pd.DataFrame(records)
by_class = tokens.groupby("class").surprisal.agg(["count", "mean", "sum"])
by_class["share of total"] = by_class["sum"] / by_class["sum"].sum()
by_class.drop(columns="sum").sort_values("share of total", ascending=False)\
    .round(3)

Most of the loss comes from a few token kinds that a trained model would predict with near certainty: which operator comes first, whether the program goes on (),) or stops (<|im_end|>), and whether the next argument is a reference ((#). The mean surprisal also falls from turn to turn as earlier answers in the chat show the format, but only a little at first: the model does not pick the format up from one or two answers. Numbers cost little, and what is left for fine-tuning is the reasoning that decides the operator and the arguments.

7.4 The number fine-tuning starts from

For the whole validation split we compute the mean surprisal of the gold tokens: one forward pass per conversation, token-weighted. This is a model run over the whole split, so it is built once as an artifact, in a subprocess.

Code 
#HEAVY
@artifact("val_gold_nll", deps=["train_val_split"], heavy=True)
def build_val_gold_nll(out, deps):
    import json

    import torch
    from transformers import AutoModelForCausalLM, AutoTokenizer

    from convfinqa.formatting import conversation_messages
    from convfinqa.probing import mean_gold_nll

    name = "Qwen/Qwen3-4B-Instruct-2507"
    tok = AutoTokenizer.from_pretrained(name)
    model = AutoModelForCausalLM.from_pretrained(
        name, dtype=torch.bfloat16, device_map="cuda"
    ).eval()
    chats = [
        conversation_messages(c)
        for c in deps["train_val_split"].jsonl("val.jsonl")
    ]
    (out / "nll.json").write_text(json.dumps(mean_gold_nll(model, tok, chats)))

val_nll = get("val_gold_nll").json("nll.json")
print(
    f"val: {val_nll['conversations']} conversations, "
    f"{val_nll['tokens']:,} answer tokens"
)
print(
    f"mean gold-program negative log-likelihood: "
    f"{val_nll['nll']:.4f} nats per token"
)

from math import exp
print(f"perplexity: {exp(val_nll['nll']):.3f}")
val: 306 conversations, 16,417 answer tokens
mean gold-program negative log-likelihood: 2.2062 nats per token
perplexity: 9.081

The perplexity is the exponential of this mean: the model is as uncertain, on average, as if it were choosing uniformly among that many tokens at each gold position. A perplexity of 1 would mean every gold token had probability 1. It is an average of a lopsided distribution (the earlier table shows a few very costly tokens among many nearly free ones), it is per token, so it depends on the tokenizer, and it covers the answer tokens only. It carries the same information as the loss; we report both because the training logs show the loss and the perplexity is easier to picture.

The mean negative log-likelihood is the loss of the untuned model on the validation split, with the data in exactly the format the training will use. Chapter 12 uses the same format, so its step-0 validation loss should agree with it within a few percent: if it doesn’t, the formatting or the label mask differs between the two, and we look there first. After training we expect the loss to fall, and the same heatmap to be much paler.

NoteUnder the hood

The loss is a mean over tokens, not over conversations or turns, so long conversations weigh more. probing.gold_logprobs scores token t with the logits at position t - 1, which is how the model’s own labels= loss is defined; Chapter 8 shows the two agree. Attention maps from a copied number back to table cells are a natural next probe, but they are only suggestive: a head that attends to a cell is not thereby the reason for the answer (Vaswani et al. 2017). We leave them out.

```{python}
    for piece, lp in zip(row["tokens"], row["logprobs"]):
        records.append({
            "class": token_class(piece),
            "turn": min(turn, 4) + 1,
            "surprisal": -lp
        })
        turn += piece == "<|im_end|>"
tokens = pd.DataFrame(records)
by_class = tokens.groupby("class").surprisal.agg(["count", "mean", "sum"])
by_class["share of total"] = by_class["sum"] / by_class["sum"].sum()
by_class.drop(columns="sum").sort_values("share of total", ascending=False)\
    .round(3)
```

```{python}
tokens.groupby("turn").surprisal.agg(["count", "mean"])\
    .rename_axis("turn (5 = 5 or later)").round(2)
```

Most of the loss comes from a few token kinds that a trained model would predict with near certainty:
which operator comes first, whether the program goes on (`),`) or stops (`<|im_end|>`), and whether the
next argument is a reference (`(#`). The mean surprisal also falls from turn to turn as earlier answers
in the chat show the format, but only a little at first: the model does not pick the format up from one
or two answers. Numbers cost little, and what is left for fine-tuning is the **reasoning** that decides
the operator and the arguments.

## The number fine-tuning starts from

For the whole validation split we compute the mean surprisal of the gold tokens: one forward pass per
conversation, token-weighted. This is a model run over the whole split, so it is built once as an
artifact, in a subprocess.

```{python}
#HEAVY
@artifact("val_gold_nll", deps=["train_val_split"], heavy=True)
def build_val_gold_nll(out, deps):
    import json

    import torch
    from transformers import AutoModelForCausalLM, AutoTokenizer

    from convfinqa.formatting import conversation_messages
    from convfinqa.probing import mean_gold_nll

    name = "Qwen/Qwen3-4B-Instruct-2507"
    tok = AutoTokenizer.from_pretrained(name)
    model = AutoModelForCausalLM.from_pretrained(
        name, dtype=torch.bfloat16, device_map="cuda"
    ).eval()
    chats = [
        conversation_messages(c)
        for c in deps["train_val_split"].jsonl("val.jsonl")
    ]
    (out / "nll.json").write_text(json.dumps(mean_gold_nll(model, tok, chats)))

val_nll = get("val_gold_nll").json("nll.json")
print(
    f"val: {val_nll['conversations']} conversations, "
    f"{val_nll['tokens']:,} answer tokens"
)
print(
    f"mean gold-program negative log-likelihood: "
    f"{val_nll['nll']:.4f} nats per token"
)

from math import exp
print(f"perplexity: {exp(val_nll['nll']):.3f}")
```

The **[perplexity](901_glossary.qmd#gloss-perplexity)** is the exponential of this mean: the model is as uncertain, on average, as if it
were choosing uniformly among that many tokens at each gold position. A perplexity of 1 would mean every
gold token had probability 1. It is an average of a lopsided distribution (the earlier table shows a few
very costly tokens among many nearly free ones), it is per token, so it depends on the tokenizer, and it
covers the answer tokens only. It carries the same information as the loss; we report both because the
training logs show the loss and the perplexity is easier to picture.

The mean [negative log-likelihood](901_glossary.qmd#gloss-nll) is the loss of the untuned model on the validation split, with the data
in exactly the format the training will use. @sec-training uses the same format, so its **step-0
validation loss** should agree with it within a few percent: if it doesn't, the formatting or the label mask differs between
the two, and we look there first. After training we expect the loss to fall, and the same
heatmap to be much paler.

::: {.callout-note title="Under the hood"}
The loss is a mean over tokens, not over conversations or turns, so long conversations weigh more.
`probing.gold_logprobs` scores token `t` with the logits at position `t - 1`, which is how the model's own
`labels=` loss is defined; @sec-fine-tuning shows the two agree.
Attention maps from a copied number back to table cells are a natural next probe, but they are only
suggestive: a head that attends to a cell is not thereby the reason for the answer
[@vaswani2017attention]. We leave them out.
:::
