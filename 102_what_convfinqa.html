2  What ConvFinQA looks like

You will learn:

  • how a ConvFinQA conversation is built from one page of an earnings report;
  • what the questions, programs and answers look like, for both conversation types;
  • how big the data is, and how long a full conversation gets in tokens, which sets max_length for training.

ConvFinQA (Chen et al. 2022) turns FinQA questions about earnings-report pages into multi-turn conversations. Each page has text before a table, the table, and text after it. A conversation asks a chain of questions about that page, and each turn has a small program in a domain-specific language (DSL) that computes the answer.

Type I conversations decompose one FinQA question into a chain of turns. First the page the model sees: the text before the table (shortened here), the table as markdown, and the text after.

2.6 The DSL

A program is a comma-separated list of steps, op(arg, arg). A turn that only selects a number has a bare number as its program. The operations are add, subtract, multiply, divide, exp and greater. (The authors’ code also lists FinQA’s table_sum, table_average, table_max and table_min, but no ConvFinQA gold program uses them.) An argument is one of:

  • a number literal copied from the page, such as 206588 or 0.14136, possibly with a % sign, such as 19%;
  • a step reference #k, the result of step k;
  • a constant from a fixed list.

The chapter on the DSL and its executor covers the grammar and the executor in detail. Here we look at what makes an argument a literal or a constant, and how the paper’s model decides what it may write.

2.6.1 Constants

The constants are not read from the page. The authors’ code defines a fixed list of constants, and every constant in the train and dev programs is in it:

Code 
import re

const_use = Counter(
    c
    for s in ["train", "dev"]
    for conv in splits[s]
    for p in conv["annotation"]["turn_program"]
    for c in re.findall(r"const_\w+", p)
)
assert set(const_use) <= set(steps.CONSTANTS)

pd.Series(
    {c: const_use.get(c, 0) for c in steps.CONSTANTS},
    name="uses (train + dev)"
).to_frame().T
const_1 const_2 const_3 const_4 const_5 const_6 const_7 const_8 const_9 const_10 const_100 const_1000 const_10000 const_100000 const_1000000 const_10000000 const_1000000000 const_m1
uses (train + dev) 132 136 138 36 28 14 12 12 18 7 1147 344 0 1 197 0 1 19

The list has 18 constants.

They are mostly scale factors and counts: const_100 turns a ratio into a percentage, const_1000 and const_1000000 convert units, and small integers such as const_3 count years for an average (the Type II example above ends with divide(#1, const_3)). The rule is by convention, not by whether the digits occur on the page: a number the question needs but does not read from the document is a constant, and the same digits read off the page are a literal.

2.6.2 Percentages and the executor

The official executor (str_to_num in the authors’ general_utils.py) strips commas and tries to read a float. If that fails and the string contains %, it removes the sign and divides by 100, so 19% is evaluated as 0.19. A const_ token is replaced by its number (const_m1 is -1). The executor never looks at the page: whether a program may use 19% at all is decided elsewhere.

2.6.3 What the paper’s decoder may write

FinQANet’s generator (Chen et al. 2022) is restricted: at each step it can emit an operator, a constant from the list, a step reference, or a number copied from its input. Its input is the question plus the context it is given (supporting text and table rows), split on spaces, and a token counts as a copyable number if, after removing commas, it parses as a number or ends with %. This is the rule, implemented in steps.copyable_numbers:

Code 
row = " ".join(conv_I["table"][-1])
print(row)
print(steps.copyable_numbers(row))
gross margin percentage 28% ( 28 % ) 23% ( 23 % ) 27% ( 27 % )
['28%', '28', '%', '23%', '23', '%', '27%', '27', '%']

This works because the page text is pre-tokenized: punctuation and symbols are separated from the surrounding text by spaces ($ 103102, june 30 , 2009, ( 2913 )), so numbers can be extracted cleanly. The exception is %, which the data keeps attached to its number in the first form (28%) and also writes as a separate token in the parenthesised form (( 28 % )). The attached 28% is a candidate. In the spaced form, 28 is a candidate and the lone % also passes the rule, which looks like an accidental quirk of the check.

Whether our own models should be restricted this way is a separate question, taken up in the constrained-decoding chapter.

2.8 How long is a conversation in tokens?

Training uses one sequence per full conversation: the system prompt, the page, and every question and answer. So the longest conversations set the memory we need. Turning a data row into token ids takes three steps:

  1. Row to messages. Our own choice, in conversation_messages (src/convfinqa/formatting.py): a system prompt, then the page and the first question as the first user message, then the gold program as the assistant’s reply, and so on for every turn. The experiments part extends this module for training.
  2. Messages to one string. The model’s own chat template, which ships with its tokenizer. It wraps each message in the special markers that the model was trained with.
  3. String to token ids. The tokenizer itself.

Here is step 2 for the clean Type I conversation from above. The page text and table are cut out so the structure is visible.

Code 
from transformers import AutoTokenizer

from convfinqa.formatting import conversation_messages

text = tok.apply_chat_template(conversation_messages(conv_I), tokenize=False)
cut = text.index("\n\nQuestion:")
print(text[:260] + "\n[... page text and table omitted ...]" + text[cut:])

NoteWhich tokenizer, and why it matters

The ConvFinQA paper doesn’t prescribe a tokenizer; it predates our model. We use the tokenizer and chat template of the model we will fine-tune, Qwen/Qwen3-4B-Instruct-2507, so that the lengths below are what training will see. The numbers, and the max_length we derive from them, belong to this tokenizer and to our formatting. A different base model would give slightly different counts, so check them again before reusing the value.

Now we count tokens for every conversation of train and dev (step 3). The count is made by convfinqa.lengths, with add_special_tokens=False because the template has already written the special tokens into the string. It is the artifact conversation_lengths, so that the chapters that need the longest conversation read it from there, and a rebuild from a clean checkout makes it again.

Code 
import pandas as pd

from convfinqa.artifacts import artifact, get


@artifact("conversation_lengths")
def build_conversation_lengths(out, deps):
    import json

    from transformers import AutoTokenizer

    from convfinqa import data
    from convfinqa.lengths import conversation_lengths, max_length_for

    tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-4B-Instruct-2507")
    rows = conversation_lengths(
        tok, {name: data.load_split(name) for name in ["train", "dev"]}
    )
    longest = max(r["tokens"] for r in rows)
    (out / "lengths.jsonl").write_text(
        "".join(json.dumps(r) + "\n" for r in rows)
    )
    (out / "lengths.json").write_text(json.dumps(
        {"longest": longest, "max_length": max_length_for(longest)}
    ))

The first turns just **select a number** from the table. Later turns compute with them. The last turn
restates the full calculation, using `#0` for "the result of step 0" so the program stays self-contained.

## The DSL

A program is a comma-separated list of steps, `op(arg, arg)`. A turn that only selects a number has
a bare number as its program. The operations are `add`, `subtract`, `multiply`, `divide`, `exp` and
`greater`. (The authors' code also lists FinQA's `table_sum`, `table_average`, `table_max` and
`table_min`, but no ConvFinQA gold program uses them.) An argument is one of:

- a **number literal** copied from the page, such as `206588` or `0.14136`, possibly with a `%`
  sign, such as `19%`;
- a **step reference** `#k`, the result of step *k*;
- a **constant** from a fixed list.

The chapter on the DSL and its executor covers the grammar and the executor in detail. Here we look
at what makes an argument a literal or a constant, and how the paper's model decides what it may write.

### Constants

The constants are not read from the page. The authors' code defines a fixed list of constants, and every
constant in the train and dev programs is in it:

```{python}
import re

const_use = Counter(
    c
    for s in ["train", "dev"]
    for conv in splits[s]
    for p in conv["annotation"]["turn_program"]
    for c in re.findall(r"const_\w+", p)
)
assert set(const_use) <= set(steps.CONSTANTS)

pd.Series(
    {c: const_use.get(c, 0) for c in steps.CONSTANTS},
    name="uses (train + dev)"
).to_frame().T
```

The list has `{python} len(steps.CONSTANTS)` constants.

They are mostly scale factors and counts: `const_100` turns a ratio into a percentage,
`const_1000` and `const_1000000` convert units, and small integers such as `const_3` count years for an
average (the Type II example above ends with `divide(#1, const_3)`). The rule is by convention, not
by whether the digits occur on the page: a number the question needs but does not read from the
document is a constant, and the same digits read off the page are a literal.

### Percentages and the executor

The official executor (`str_to_num` in the authors' `general_utils.py`) strips commas and tries to
read a float. If that fails and the string contains `%`, it removes the sign and divides by 100, so
`19%` is evaluated as 0.19. A `const_` token is replaced by its number (`const_m1` is -1). The
executor never looks at the page: whether a program may use `19%` at all is decided elsewhere.

### What the paper's decoder may write

FinQANet's generator [@chen2022convfinqa] is restricted: at each step it can emit an operator, a
constant from the list, a step reference, or a number **copied from its input**. Its input is the
question plus the context it is given (supporting text and table rows), split on spaces, and a token counts as a copyable number if, after
removing commas, it parses as a number *or ends with `%`*. This is the rule, implemented in
`steps.copyable_numbers`:

```{python}
row = " ".join(conv_I["table"][-1])
print(row)
print(steps.copyable_numbers(row))
```

This works because the page text is pre-tokenized: punctuation and symbols are separated from the
surrounding text by spaces (`$ 103102`, `june 30 , 2009`, `( 2913 )`), so numbers can be extracted
cleanly. The exception is `%`, which the data keeps attached to its number in the first form
(`28%`) and also writes as a separate token in the parenthesised form (`( 28 % )`). The attached
`28%` is a candidate. In the spaced form, `28` is a candidate and the lone `%` also passes the rule,
which looks like an accidental quirk of the check.

Whether our own models should be restricted this way is a separate question, taken up in the
constrained-decoding chapter.

## How long is a conversation in tokens?

Training uses one sequence per **full conversation**: the system prompt, the page, and every question and
answer. So the longest conversations set the memory we need. Turning a data row into token ids takes
three steps:

1. **Row to messages.** Our own choice, in `conversation_messages` (`src/convfinqa/formatting.py`): a
   system prompt, then the page and the first question as the first user message, then the gold
   program as the assistant's reply, and so on for every turn. The experiments part extends this
   module for training.
2. **Messages to one string.** The model's own **[chat template](901_glossary.qmd#gloss-chat-template)**, which ships with its tokenizer. It
   wraps each message in the special markers that the model was trained with.
3. **String to token ids.** The tokenizer itself.

Here is step 2 for the clean Type I conversation from above. The page text and table are cut out
so the structure is visible.

```{python}
from transformers import AutoTokenizer

from convfinqa.formatting import conversation_messages

tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-4B-Instruct-2507")

text = tok.apply_chat_template(conversation_messages(conv_I), tokenize=False)
cut = text.index("\n\nQuestion:")
print(text[:260] + "\n[... page text and table omitted ...]" + text[cut:])
```

The `<|im_start|>` and `<|im_end|>` markers delimit each message and carry its role. The model learns
to end every answer with `<|im_end|>`, and that token is part of what we train on.

::: {.callout-note title="Which tokenizer, and why it matters"}
The ConvFinQA paper doesn't prescribe a tokenizer; it predates our model. We use the tokenizer and
chat template of the model we will fine-tune, `Qwen/Qwen3-4B-Instruct-2507`, so that the lengths
below are what training will see. The numbers, and the `max_length` we derive from them, belong to
this tokenizer and to our formatting. A different base model would give slightly different counts, so
check them again before reusing the value.
:::

Now we count tokens for every conversation of `train` and `dev` (step 3). The count is made by
`convfinqa.lengths`, with `add_special_tokens=False` because the template has already written the special
tokens into the string. It is the artifact `conversation_lengths`, so that the chapters that need the longest
conversation read it from there, and a rebuild from a clean checkout makes it again.

```{python}
import pandas as pd

from convfinqa.artifacts import artifact, get


@artifact("conversation_lengths")
def build_conversation_lengths(out, deps):
    import json

    from transformers import AutoTokenizer

    from convfinqa import data
    from convfinqa.lengths import conversation_lengths, max_length_for

    tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-4B-Instruct-2507")
    rows = conversation_lengths(
        tok, {name: data.load_split(name) for name in ["train", "dev"]}
    )
    longest = max(r["tokens"] for r in rows)
    (out / "lengths.jsonl").write_text(
        "".join(json.dumps(r) + "\n" for r in rows)
    )
    (out / "lengths.json").write_text(json.dumps(
        {"longest": longest, "max_length": max_length_for(longest)}
    ))


lengths = pd.DataFrame(get("conversation_lengths").jsonl("lengths.jsonl"))
lengths.groupby("split").tokens.describe(percentiles=[0.5, 0.9, 0.99, 0.999])\
    .round(0)
```

```{python}
#| fig-cap: "Tokens per full conversation."
lengths.groupby("split").tokens.plot.hist(
    bins=60, alpha=0.6, legend=True, figsize=(6, 3)
)
plt.xlabel("tokens in conversation")
plt.tight_layout()
```

We pick `max_length` as the longest conversation rounded up to a multiple of 256, so that no training
conversation is truncated. Truncating would cut off assistant tokens, which are exactly what the loss
is computed on. The value is saved in the same artifact for later chapters, since stages pass data through files.

```{python}
chosen = get("conversation_lengths").json("lengths.json")
print(
    f"longest conversation: {chosen['longest']} tokens"
    f" -> max_length = {chosen['max_length']}"
)
```

Notice how numbers like `206588` cost one token per digit in this tokenizer. The foundations part looks at
tokenization properly. It is one reason the model writes a program and a Python executor does the
arithmetic.
